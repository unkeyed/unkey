Retrieve a custom domain by ID or name and its <Tooltip tip="Here: proving DNS ownership of a custom domain. Not key verification.">verification</Tooltip> status. Names are unique per workspace, so `api.acme.com` is enough. No <Tooltip tip="A group of apps, usually one per codebase or product.">project</Tooltip>, <Tooltip tip="A Compute app: a deployable service inside a project. Not your application in general.">app</Tooltip>, or <Tooltip tip="A production or preview environment of a Compute app, not the dashboard label on a key.">environment</Tooltip> is needed.

Use it to check progress after `unkey domains create`. We check DNS about once a minute.

- `status: verified` means routing is set up and a certificate has been requested.
- Each entry in `dnsRecords` has a `verified` flag, so you can see which records are still missing. A routing record your provider proxies or flattens can stay `false` even while it serves traffic.
- `verificationError` explains the last failed check.
- Verification stops 24 hours after `createdAt`, and the status becomes `failed`.

## Usage

```bash
unkey domains get --domain=<domain id or name>
```

## Required permissions

Your root key needs one of:

- `environment.*.read_domain` (any environment)
- `environment.<environment_id>.read_domain` (a specific environment)

If the domain doesn't exist or your key doesn't have the permission, you get the same 404: `The requested domain does not exist.` See [Root key permissions](/platform/root-keys/permissions) for the full catalog.

## Examples

Check a domain:

```bash
unkey domains get --domain=api.acme.com
```

Print only the status:

```bash
unkey domains get --domain=api.acme.com --output=json | jq -r '.data.status'
```

## API endpoint

The command calls [`POST /v2/domains.getDomain`](/compute/api-reference/domains/get-domain) and prints its response. The request fields carry the same names as the flags in camelCase, which is the shape `--body` expects.
