Start a deployment that was stopped with `unkey deployments stop`, so it serves traffic again. Nothing is rebuilt, and it keeps the configuration it had. You don't need to wait for `stopped`: a deployment that's still shutting down can be started right away. The command returns before the deployment is back. Poll `unkey deployments get` until the status is `ready`.

Starting a deployment needs an active Compute plan. Without one the API answers 412 with `The workspace has no active Compute plan.` A workspace over its Compute spend cap gets `The workspace is suspended by its Compute spend cap. Raise the spend limit to resume.` See [Compute plans](/compute/get-started/plans).

## Usage

```bash
unkey deployments start --deployment-id=<deployment id>
```

## Required permissions

Your root key needs write on the deployment:

- `unkey:v1:<workspace_id>:projects/<project_id>/apps/<app_id>/environments/<environment_id>/deployments/<deployment_id>#write`

If the deployment doesn't exist or your key doesn't have the permission, you get the same 404: `The requested deployment does not exist.` If your key can read the deployment, you get a 403 that names the missing permission instead. See [Root key permissions](/platform/root-keys/permissions) for the full catalog.

## Examples

Start a stopped deployment:

```bash
unkey deployments start --deployment-id=d_1234abcd
```

Send the request body as JSON:

```bash
unkey deployments start --body='{"deploymentId":"d_1234abcd"}'
```

## API endpoint

The command calls [`POST /v2/deployments.startDeployment`](/compute/api-reference/deployments/start-deployment) and prints its response. The request fields carry the same names as the flags in camelCase, which is the shape `--body` expects.
