Deploy a prebuilt container image to an <Tooltip tip="A Compute app: a deployable service inside a project. Not your application in general.">app</Tooltip> and wait until it's live or has failed. It's a shortcut for [deployments create](/compute/cli/deployments/create-deployment) followed by polling [deployments get](/compute/cli/deployments/get-deployment).

<Warning>
  `unkey deploy` relies on endpoints that aren't part of the public API reference and can change without notice. For scripts that must not break, use the `unkey deployments` commands, which call the stable `deployments.*` endpoints.
</Warning>

## Usage

```bash
unkey deploy <docker-image> --project=<project> [flags]
```

The image is required. Without it, the command exits with `docker image is required`. The image must already be in a registry we can pull from. Nothing is built.

## Flags

<ParamField body="--project" type="string" required>
  <Tooltip tip="A group of apps, usually one per codebase or product.">Project</Tooltip> slug the app belongs to. Falls back to `UNKEY_PROJECT`.
</ParamField>

<ParamField body="--app" type="string" default="default">
  App slug within the project. Falls back to `UNKEY_APP`.
</ParamField>

<ParamField body="--env" type="string" default="preview">
  Slug of the <Tooltip tip="A production or preview environment of a Compute app, not the dashboard label on a key.">environment</Tooltip> to deploy to. Pass `production` to deploy to production.
</ParamField>

<ParamField body="--keyspace-id" type="string">
  Keyspace whose keys the gateway accepts for this deployment. Falls back to `UNKEY_KEYSPACE_ID`. See [API key authentication](/compute/gateway/api-key-auth).
</ParamField>

<ParamField body="--branch" type="string" default="main">
  Git branch recorded on the deployment. If you leave the default and you're in a Git checkout on another branch, the CLI uses that branch.
</ParamField>

<ParamField body="--commit" type="string">
  Accepted, but not sent in the deployment request. The command reads commit metadata from the checkout's HEAD regardless of this flag. Outside a Git repository, it sends no commit metadata.
</ParamField>

<ParamField body="--root-key" type="string">
  Root key. Falls back to `UNKEY_ROOT_KEY`, then the CLI session from `unkey login` when that session belongs to this API, then a root key saved with `unkey login --root-key`.
</ParamField>

<ParamField body="--api-base-url" type="string">
  API base URL. Falls back to `UNKEY_API_BASE_URL`. When empty, a CLI session is sent to the API URL stored at login, and a root key uses `https://api.unkey.com`. A different host skips the stored session.
</ParamField>

The command doesn't accept `--output`, `--config`, or `--body`.

## Required permissions

`project.*.create_deployment` or `project.<project_id>.create_deployment` to create the deployment, and `project.*.read_deployment` or `project.<project_id>.read_deployment` to follow it. These are project permissions. The `unkey deployments` commands use different permissions, listed on each command's page. See [Root key permissions](/platform/root-keys/permissions).

## What you'll see

The command writes the project, app, environment, image, and progress messages to stderr. Final deployment details and domains go to stdout. Inside a Git repository, it sends the branch and available HEAD metadata, including the commit SHA, message, author, and commit time. It doesn't send a dirty-checkout marker.

Spinners and colors appear only when stderr is a terminal. With redirected stderr or `TERM=dumb`, progress is plain text without spinners or color codes. Set `NO_COLOR` to any nonempty value to disable color in a terminal; the spinner can still run.

If the deployment can't be created, the command writes the error to stderr and exits 1. Common causes are a `--project` or `--app` that doesn't exist, an `--env` that isn't an environment of that app, a root key without `create_deployment`, an image reference we can't parse, or a `--keyspace-id` that isn't in your workspace.

Otherwise it follows the deployment until it finishes:

- **Ready:** prints the final deployment details and domains to stdout and exits 0. Progress completion stays on stderr.
- **Failed:** writes the error message (or `Unknown deployment error`) to stderr and exits 1, so a CI job fails.
- **Still going after 5 minutes:** exits with `deployment timeout after 5 minutes`. The deployment keeps going. Follow it with `unkey deployments get`.

## Examples

Deploy to the preview environment of the default app:

```bash
unkey deploy ghcr.io/acme/payments:1.4.2 --project=payments --root-key=unkey_xxx
```

Deploy to production with the key from the environment, as in CI:

```bash
export UNKEY_ROOT_KEY=unkey_xxx
unkey deploy myregistry.io/payments-api:latest --project=payments --app=payments-api --env=production
```

Save the final result separately from plain progress output:

```bash
unkey deploy ghcr.io/acme/payments:1.4.2 --project=payments \
  >deployment.txt 2>deployment-progress.log
```

Deploy behind API key authentication:

```bash
unkey deploy ghcr.io/acme/payments:1.4.2 --project=payments --app=payments-api --env=production --keyspace-id=ks_1234abcd
```
