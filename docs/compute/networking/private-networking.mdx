title: Private networking
description: "Reach your own instances and other apps in the same project over private DNS instead of public domains."
---

Private networking lets instances talk to each other directly, with hostnames in the `unkey.internal` zone. Private traffic doesn't use public domains and doesn't pass through the [gateway](/compute/gateway/overview).

A <Tooltip tip="One built and running version of an app in one environment.">deployment</Tooltip> can reach two kinds of private hostname:

- Its own instances, through `UNKEY_PRIVATE_DOMAIN`. This needs no setup.
- Another app in the same project, through an app [connection](/compute/concepts/connections).

<Note>
  Private networking is in beta. Behavior on this page can change.
</Note>

## Private DNS

Every deployment created with private networking uses the cluster's DNS resolver for private and public hostnames. A deployment gets private DNS even when its app has no connections.

Unkey assigns deployment-specific hostnames and supplies them in environment variables. Read those variables instead of constructing hostnames from app or connection names. Resolving a hostname doesn't grant access to its instances. Network access still requires a saved app connection, except between instances of the same deployment.

## Reach instances of the same deployment

Unkey sets `UNKEY_PRIVATE_DOMAIN` to a hostname for this deployment's own instances, without a scheme or port. It resolves to the ready instances of the same deployment, including instances in other regions. It doesn't include older or newer deployments of the app.

Each deployment has its own hostname. It stays the same when an instance restarts or your app's name or slug changes.

Instances of a deployment can reach each other through this hostname on every TCP and UDP port. Use it for peer discovery, clustering, or messages to every instance. You don't need a connection.

Unkey sets `UNKEY_PRIVATE_DOMAIN` when all of these are true:

- The deployment was created with private networking. Redeploy deployments that were created before it.
- The instance's region has private DNS.

When the variable is missing, the deployment has no private DNS, so its app connection hostnames don't resolve either.

## Connect to another app

To call another app in the same project, add an app connection to your app. The examples on this page use a `web` app that calls a `payments` app on port 8080.

1. Open `web` and navigate to **Connections**.
2. Select the environment in the environment selector. The page opens on production.
3. Click **Add connection**, then click **App**.
4. Select `payments`.
5. Click **Add connection**.
6. Redeploy `web` in that environment.

The new deployment of `web` gets `PAYMENTS_HOST`, containing its deployment-specific hostname for the connection.

Like every connection, an app connection applies only to deployments created after you add or change it. See [Making changes to connections](/compute/concepts/connections#making-changes-to-connections).

<Note>
  If your app deploys from a container image, a preview app connection needs a **Target environment** when you add it. Image deployments have no Git branch to match.
</Note>

### Use the hostname

The variable holds a hostname only, without a scheme or port. Combine it with the port that the target listens on. Unkey doesn't inject the target's port, so store it in a [variable](/compute/configure/environment-variables) or in your code.

<CodeGroup>

```javascript Node.js
const host = process.env.PAYMENTS_HOST;
const port = process.env.PAYMENTS_PORT ?? "8080";

const response = await fetch(`http://${host}:${port}/charges`);
```

```python Python
import os
import urllib.request

host = os.environ["PAYMENTS_HOST"]
port = os.environ.get("PAYMENTS_PORT", "8080")

url = f"http://{host}:{port}/charges"
with urllib.request.urlopen(url, timeout=5) as response:
    body = response.read()
```

</CodeGroup>

The same pattern works for any TCP or UDP protocol. Pass the hostname and port to your gRPC client, queue client, or other driver.

### Hostnames and variables

Unkey names an app connection after the target app's slug. If that name is taken, it adds a number, such as `payments-2`. The reserved name `self` becomes `self-2`. If the slug doesn't start with a letter, or starts with `unkey`, Unkey adds an `app-` prefix. You can rename an app connection.

The name sets the variable. To build it, Unkey converts the name to uppercase, replaces hyphens with underscores, and adds `_HOST`. Its hostname value is assigned separately for each deployment.

| Name | Variable |
| --- | --- |
| `payments` | `PAYMENTS_HOST` |
| `event-store` | `EVENT_STORE_HOST` |

A name must follow these rules:

- Starts with a lowercase letter
- Contains only lowercase letters, numbers, and hyphens
- Ends with a letter or number
- Has at most 63 characters
- Doesn't start with `unkey`
- Isn't `self`, which belongs to [your deployment's own instances](#reach-instances-of-the-same-deployment)
- Is unique among your app's connections in that environment

Your app can have one app connection per target app in each environment. If one of your [environment variables](/compute/configure/environment-variables) has the same name as an app connection variable, the app connection variable wins.

### Choose which deployment you reach

The target app has many deployments. The app connection's target decides which one the hostname reaches. To change it, select the app connection on the **Connections** page and choose an option from **Target**.

| Target | Reaches |
| --- | --- |
| **production** | The target app's live production deployment. It follows promotions and rollbacks. This is the default in your app's production environment. |
| **Same Git branch** | Preview only. The target app's newest preview deployment from your deployment's Git branch and repository fork. This is the default in your app's preview environment. |
| **preview** | The target app's newest preview deployment from any branch. |
| **Specific deployment…** | One deployment that you pick. It must be ready and running when you pick it. |

"Newest" means the most recently created deployment that has reached ready at least once. A deployment that is still building doesn't take over the hostname.

Your deployment saves the target, not an address. **production**, **Same Git branch**, and **preview** keep following the target app. When `payments` deploys, promotes, or rolls back, the hostname in a running `web` deployment moves to the deployment that the target selects now. Only **Specific deployment…** stays on one deployment.

The selected deployment must be running and have ready instances. If it has stopped, for example after a preview went idle, the hostname fails to resolve. Unkey doesn't fall back to an older running deployment, and private traffic can't wake a stopped preview. Wake or redeploy the target app, or choose another target and redeploy your app.

**Same Git branch** needs a deployment of your app built from a Git branch. If the target app has no preview for that branch, the hostname doesn't resolve until you deploy one or choose another target. If your app deploys from a container image, choose **production**, **preview**, or a specific deployment.

### Pinned deployments keep running

**Specific deployment…** pins one deployment of the target app. Use a pin to hold a known version while you test or migrate.

Unkey doesn't stop a pinned deployment automatically while a pin holds it. It skips replacement stops and idle stops, so the deployment keeps using resources. A pin holds while either of these is true:

- An app connection on the **Connections** page pins it.
- A deployment of your app that saved the pin is running or still deploying. A deployment that waits for approval doesn't hold a pin.

To release a pin, change the target and redeploy your app. The pin releases when no running deployment of your app has it saved. The pinned deployment's page lists the app connections that keep it running.

You can still stop a pinned preview deployment yourself. The hostname then stops resolving. New deployments of your app fail while an app connection pins a deployment that isn't running, so change the target or wake the deployment first.

### Access rules

Traffic between deployments is denied unless an app connection allows it. An app connection allows traffic with these rules:

- From your deployment to the target deployment, in one direction only
- On every TCP and UDP port of the target
- Only between apps in the same project
- Only for deployments of your app that saved the app connection

For `payments` to call `web`, add an app connection on `payments`. Sharing a project or an environment type doesn't grant access by itself.

Private traffic skips the gateway, so gateway policies such as [API key authentication](/compute/gateway/api-key-auth) and [rate limiting](/compute/gateway/rate-limiting) don't apply to it. Unkey doesn't issue TLS certificates for `unkey.internal` hostnames. If private traffic needs encryption or authentication, configure it in your apps.

### Listen for private traffic

The target app must listen on all IPv4 interfaces (`0.0.0.0`), not only on `localhost`. Most apps that already serve public traffic on `PORT` need no change.

The target can also serve extra ports for private callers only. Public traffic reaches only the configured [port](/compute/configure/runtime-settings). For example, `payments` can serve HTTP on port 8080 and gRPC on port 9090 for connected apps.

### Rename or remove an app connection

Select an app connection on the **Connections** page to see its variable name, rename it, change its target, or remove it. Read the hostname value from the running deployment's variable. Every change applies to the next deployment of your app.

- Rename: update your code to read the new variable before you redeploy. Running deployments keep the old name.
- Remove: future deployments don't get the app connection. Running deployments keep it until they stop.
- Delete the target app: Unkey deletes app connections that target it. Saved app connections to it stop resolving.

## How private DNS answers

Private DNS answers follow these rules:

- Answers contain IPv4 (`A`) records only. Lookups for IPv6 (`AAAA`) records return no addresses.
- Addresses come back in random order. Clients that use the first address spread connections across instances. Unkey doesn't add a load balancer in front of private traffic.
- Answers have a 5 second TTL. Resolve the hostname again when you open new connections.
- A name that isn't published returns `NXDOMAIN`.
- A connection whose target has no ready instances returns no usable address. Your DNS client can report a missing name or an empty answer.

### Choose a region

Prefix the injected hostname with a region name to reach only instances in that region:

| Hostname in your code | Answers |
| --- | --- |
| `PAYMENTS_HOST` | All ready instances of the target deployment |
| `"eu-west-1." + PAYMENTS_HOST` | Ready instances in `eu-west-1` only, with no fallback |

Use `UNKEY_REGION` as the prefix to select your own region. The same prefix works with `UNKEY_PRIVATE_DOMAIN` for your deployment's own instances. The injected variable stays unchanged.

A region with no ready instances returns no addresses, even when other regions have ready instances. There is no local-first or nearest-region fallback.

## When the target changes

The hostname moves when the target selects another deployment, for example after the target app deploys, promotes, or rolls back. Each region switches on its own after the new deployment has ready instances. Until then, the hostname keeps its previous answer.

Unkey doesn't move open connections. Your app can reach the previous deployment for up to 30 minutes after a switch, but only while that deployment runs. A replaced preview is scheduled to stop 1 minute after a new deployment replaces it on its branch, even when an app connection follows it. A deployment that a [specific deployment pin](#pinned-deployments-keep-running) holds doesn't stop automatically. See [Automatic stops](/compute/concepts/production-and-preview#automatic-stops). Resolve the hostname again and reconnect to reach the new deployment.

If the target selects no running deployment, for example because the selected preview stopped, the hostname returns no usable address. It doesn't fall back to an earlier deployment.

## Limitations

Private networking has these limits:

- Only TCP and UDP over IPv4. ICMP (`ping`), SCTP, broadcast, and multicast traffic is denied.
- Only apps in the same project.
- No TLS certificates for `unkey.internal` hostnames.
- Private traffic can't wake a stopped deployment.
