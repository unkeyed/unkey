Private networking lets an app call another app in the same project directly, with a private hostname instead of a public domain. An app connection grants named, one-way access from a calling app to a target app.

<Note>
  Private networking isn't generally available. The **Connections** page appears only for workspaces that have private networking enabled. Behavior on this page can change before general availability.
</Note>

## How it works

A connection gives the calling app a hostname in the `unkey.internal` zone and a variable that holds it. For a connection named `payments`, the calling app receives:

```bash
PAYMENTS_HOST=payments.unkey.internal
```

When the calling app looks up the hostname, Unkey's private DNS returns the IPv4 addresses of the ready instances of one target deployment. Answers can include instances in connected regions. Unkey chooses that deployment from the connection's [target](/compute/networking/private-networking/connections#choose-a-target). By default, a production caller reaches the target's live production deployment, and a preview caller reaches the target's preview from the same Git branch.

The connection allows traffic from the calling app to the target app on every TCP and UDP port. Traffic goes directly between instances. It doesn't pass through public domains or the [gateway](/compute/gateway/overview).

## Scope and isolation

Traffic between deployments is denied unless a connection allows it. Connections follow these rules:

- Both apps must belong to the same project.
- Each connection belongs to one environment of the calling app. Production and preview have separate connections.
- Access goes in one direction only. For the target app to call the calling app, add a connection on the target app.
- Hostnames are scoped to the calling app and environment. A deployment without the connection can't resolve the hostname, and two apps can use the same connection name for different targets.
- Sharing a project or an environment type doesn't grant network access.

Private traffic skips the gateway, so gateway policies such as [API key authentication](/compute/gateway/api-key-auth) and [rate limiting](/compute/gateway/rate-limiting) don't apply to it. Unkey doesn't issue TLS certificates for `unkey.internal` hostnames. If a private connection needs encryption or authentication, configure it in your apps.

## Connect two apps

A connection needs two apps in the same project. The target app must have a deployment that the connection can select, for example a live production deployment.

1. Open the calling app and navigate to **Connections**.
2. Select the calling app's environment from **Environment**.
3. Click **Add connection**, then click **App**.
4. Select the target app.
5. Click **Add connection**.
6. Redeploy the calling app in that environment.

Unkey names the connection after the target app's slug. For example, a target app with the slug `payments` produces the variable `PAYMENTS_HOST`. Select the connection on the canvas to view its variable and hostname, rename it, or [change its target](/compute/networking/private-networking/connections#choose-a-target).

The variable reaches the calling app with its next deployment. Existing deployments that already use private DNS can resolve new connections, but don't receive new variables. Redeploy callers that started before the workspace had private networking to configure private DNS too.

<Note>
  If the calling app deploys from a container image instead of a Git repository, a preview connection needs a **Target environment**. There's no Git branch to match automatically.
</Note>

## Use the hostname in your app

The variable holds a hostname only, without a scheme or port. Combine it with the port that the target app listens on. This can be its configured [port](/compute/configure/runtime-settings#container) or an extra private port. Unkey doesn't inject the target's port, so store it in a [variable](/compute/configure/environment-variables) or in your code.

<CodeGroup>

```javascript Node.js
const host = process.env.PAYMENTS_HOST;
const port = process.env.PAYMENTS_PORT ?? "8080";

const url = `http://${host}:${port}/charges`;
const response = await fetch(url);
```

```python Python
import os
import urllib.request

host = os.environ["PAYMENTS_HOST"]
port = os.environ.get("PAYMENTS_PORT", "8080")

url = f"http://{host}:{port}/charges"
with urllib.request.urlopen(url, timeout=5) as response:
    body = response.read()
```

</CodeGroup>

The same pattern works for any TCP or UDP protocol. Pass the hostname and port to your database driver, gRPC client, or queue client.

### Listen for private traffic

The target app must listen on all IPv4 interfaces (`0.0.0.0`), not only on `localhost`. Most apps that already serve public traffic on `PORT` need no change.

A connection allows every TCP and UDP port, so the target app can serve extra ports for private callers only. Public traffic reaches only the configured port. For example, an app can serve HTTP on its configured port 8080 and gRPC on port 9090 for connected apps.

### DNS behavior

Private DNS answers follow these rules:

- Answers contain IPv4 (`A`) records only. Lookups for IPv6 (`AAAA`) records return no addresses.
- Addresses come back in random order. Clients that use the first address spread connections across instances. Unkey doesn't add a load balancer in front of private traffic.
- Answers have a short TTL. Resolve the hostname again when you open new connections. Existing connections aren't moved when the target changes.

### Choose a region

Prefix the connection hostname to select where ready instances run:

| Hostname | Answers |
| --- | --- |
| `payments.unkey.internal` | All ready instances of the selected deployment |
| `local-first.payments.unkey.internal` | Ready instances in the caller's region, or all ready instances if none are local |
| `eu-west-1.payments.unkey.internal` | Ready instances in `eu-west-1` only, with no fallback |

Use the region name shown in `UNKEY_REGION`. All forms use the same connection
and target deployment. They don't grant access to another app or deployment.
The injected `PAYMENTS_HOST` value stays `payments.unkey.internal`; opt in with
`local-first.${PAYMENTS_HOST}` or a region prefix in your code.

`local-first` doesn't mix remote addresses into a nonempty local answer. It
selects by region, not measured latency or load. If the region catalog is
unavailable, it uses ready instances known to be in the caller's cluster, then
falls back to all ready instances. An explicit region with no known ready
instances returns `SERVFAIL`, even if other regions have ready instances.

DNS readiness and client caches can lag behind a failure. The TTL isn't a
failover deadline, and existing connections don't move to another region.

## Connect instances of the same deployment

Eligible deployments in a workspace with private networking get the `UNKEY_PRIVATE_DOMAIN` variable, set to `<app-slug>.unkey.internal`. The value is a hostname, without a scheme or port. It resolves to the ready instances of that same deployment, including those in connected regions. It doesn't include older or newer deployments of the app.

Instances of a deployment can reach each other through this hostname on every TCP and UDP port. Use it for peer discovery, clustering, or sending messages to every instance. You don't need to add a connection for it.

Unkey sets `UNKEY_PRIVATE_DOMAIN` when all of these are true:

- The workspace has at least one connection between two apps.
- The app slug is a valid DNS label: up to 63 lowercase letters, numbers, and hyphens, starting and ending with a letter or number.
- The instance was configured with private networking enabled. Redeploy apps that were already running to add it.

Connection names can't reuse the calling app's own slug, because that name belongs to `UNKEY_PRIVATE_DOMAIN`.

## Limitations

Private networking has these limits:

- Only TCP and UDP over IPv4. ICMP (`ping`), SCTP, broadcast, and multicast traffic is denied.
- Only apps in the same project.
- Only running deployments can be connection targets.
- No TLS certificates for `unkey.internal` hostnames.
