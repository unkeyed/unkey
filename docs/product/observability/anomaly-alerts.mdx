title: "Anomaly alerts"
description: "Detect unusual traffic, resource use, and instance failures in production apps"

Anomaly alerts identify behavior in an Unkey Deploy production app that differs
from its recent baseline or crosses a health limit. Use them to find traffic
changes, error spikes, resource pressure, and failed instances without setting
a fixed limit for every app.

<Note>
  Anomaly alerts are in beta and enabled per workspace. If your workspace does
  not show **Alerts** or the **Anomalies** tab, ask Unkey to enable the beta.
</Note>

Alerts apply only to production environments. Preview activity does not create
alerts.

## Understand detected metrics

Each alert identifies one metric for one app and production environment.

| Metric | What the alert means |
| --- | --- |
| 5xx errors | The server-error ratio increased above its recent level. |
| 4xx errors | The client-error ratio increased above its recent level. |
| Requests | Request volume increased above its recent level. |
| Request drop | Request volume stayed far below a recent active level. |
| Egress | Outbound network bytes increased above their recent level. |
| CPU | CPU seconds increased above their recent level. |
| Memory | Average memory utilization across instances reached 90%. |
| OOM killed | At least one instance was terminated because it ran out of memory. |
| Crash loop | At least one instance entered `CrashLoopBackOff`. |

An alert belongs to the app and environment, not one deployment. The alert
records the active deployment as context and stays open across a redeploy. This
lets you see whether a rollout helped without splitting one incident into
separate alerts.

## Understand the baseline

Unkey evaluates closed 5-minute windows and compares them with up to 24 hours of
earlier activity. It waits one full bucket before evaluating a window so normal
telemetry delivery lag does not look like missing traffic. An alert normally
appears 5 to 10 minutes after the affected bucket closes.

When anomaly rollups are installed, Unkey replays the latest 7 days of closed
telemetry before live collection starts. Only the 5-minute bucket in progress
during setup can be absent. Existing apps therefore start with a full 24-hour
baseline and enough history for request-drop detection. An app younger than 1
hour cannot create a baseline-based spike alert. An app younger than 6 hours
cannot create a request-drop alert. Unkey uses the app creation time and does
not treat earlier time as zero.

Request, egress, and CPU spikes can open after one unusual window. Moderate 4xx
and 5xx error increases must continue for two windows. Request drops must also
continue for two windows. A severe 5xx window can open immediately when at least
half of requests fail and there are at least 50 failures.

Error alerts use the percentage of requests that failed. They also require at
least 20 more failures than the recent baseline predicts. This avoids an alert
when a large percentage change affects only a few requests.

Unkey tracks request and resource completeness separately for every region
active during the latest 2 hours. A source is complete only when every active
region has finished the window. A region with no telemetry for 2 hours becomes
inactive, so a decommissioned region does not block detection. A source with no
active region is incomplete. An incomplete window cannot open or resolve an
alert.

Instance failures are sparse events. A received OOM or crash-loop event can
open an alert immediately. When there is no event, resource completeness tells
the detector whether the empty window is safe to use for recovery.

Request-drop alerts require a live deployment and at least one topology region
set to running. No live deployment, a stopped deployment, or every topology
region being stopped suppresses the alert. Setting
`autoscaling_replicas_min = 0` does not suppress detection. Scale-to-zero
capability alone does not make a traffic drop expected.

## Read the Anomalies tab

Open a project, select an app, and click **Anomalies**. Select the production
environment with the environment control.

The 7-day overview strip shows hourly behavior. Use the range selector to view
the last 24 hours, 6 hours, or 7 days in detail. Select 5xx, 4xx, Requests,
Egress, CPU, Memory, or Health to change the chart.

The solid line is the observed value. The dashed expected line and band show
the recent baseline and normal range for that bucket. Requests also show a
lower traffic boundary. Memory shows a fixed 90% limit. The Health chart shows
OOM and crash-loop events as bars.

The chart follows the same calculations as the detector. It pads the baseline
from the app creation time, aligned to 5 minutes and limited to the latest 24
hours. Eligibility counts observed 5-minute buckets even on the hourly chart.
The expected spike band needs 12 observed buckets. The request lower boundary
needs 72 observed buckets, 9 active buckets among the previous 12, and a drop of
at least 200 requests.

Error variation excludes buckets with no requests. The request lower boundary
uses the inclusive median of the previous 12 buckets, which averages the two
middle values. CPU and egress use each container's non-negative 5-minute counter
change and sum the containers. Hourly points sum those 5-minute changes. Memory
first averages samples per container, then containers per instance, and gives
every instance equal app-level weight.

Shaded regions mark all anomaly windows. Markers attached to the line identify
alerts for the selected metric. Toggle deployment markers to compare changes
with rollouts, and drag across the chart to zoom into a smaller time range.

The range list includes open and resolved alerts. Use **Load more** to retrieve
another page. A visible notice tells you when additional rows exist beyond the
pages loaded so far. Select an alert to open focus mode. The details card shows
its status, metric, observed value, expected baseline, detection window, and
deployment context. For a resolved alert, it also shows the resolution message.

## Use the alerts inbox

Open **Alerts** in the workspace navigation to see open anomalies across
production apps. The inbox does not include resolved alerts. Use the metric and
app filters to narrow the list. Each row includes recent context and a
sparkline.

Select an alert to open the affected app, environment, metric, and time range in
focus mode. When the detector resolves it, the alert leaves the workspace inbox.
Its app-level focus URL remains available with `?alert=<id>`.

## Understand alert resolution

Alerts are read-only in the dashboard. The detector resolves an alert without a
user action and displays the reason in the alert details.

An alert resolves when the metric returns to its opening baseline for three
consecutive complete windows. Memory must fall below 85% for recovery. Unkey
uses the baseline captured when the alert opened, so a continuing incident
cannot satisfy this recovery rule as its rolling baseline changes.

When behavior stays at a new level for 24 hours, the rolling baseline contains
only that new level. This can happen after a permanent and expected change, such
as traffic doubling. The detector closes the old alert with
`Baseline adapted after 24 hours` so later changes can be compared with the new
baseline.

An open request-drop alert resolves with `Deployment stopped` when there is no
live deployment, the deployment is stopped, or every topology region is
stopped. A normal recovery uses
`Metric returned to baseline for 3 consecutive windows`.

Deleting an app or environment also resolves its open alerts with
`Deployment stopped` before removing it. If metadata is already missing, the
detector finds and resolves the orphaned alerts during a later check.

Open a resolved alert through its app Anomalies deep link with `?alert=<id>`.
The focus card shows its **Resolved** status, resolution timestamp, and
resolution message.

## Know the beta limits

Anomaly alerts provide evidence for investigation, not a diagnosis. A traffic
or resource change can be expected for your workload.

This beta does not include:

- A notification service. Alerts, including 4xx alerts, are persisted but do
  not send email, Slack, or webhook notifications.
- Per-app mute controls.
- A sensitivity control in the dashboard.
- Seasonal baselines for daily or weekly patterns.
- Latency anomalies.
- Guaranteed delivery of OOM and crash-loop events. The event buffer can drop a
  lifecycle event under pressure, which causes a missed alert rather than a
  stuck alert.
- Persisted raw error and request counts. Error alerts store the ratio, while raw
  counts appear only in internal logs.
- Measured capacity results for 1 million monitored groups. Current figures are
  extrapolated from the 100,000-group test.
- Automatic before-and-after deployment comparison.

Use [runtime logs](/observability/logs),
[request details](/observability/requests), and
[deployment metrics](/observability/metrics) to investigate the affected
window.
