title: "Anomaly alerts"
description: "Detect unusual traffic, resource use, and instance failures in production apps"

Anomaly alerts flag app behavior that differs from its recent baseline or crosses a fixed health limit. Use them to catch traffic shifts, error spikes, resource pressure, and failed instances without setting a manual limit for every app.

<Note>
  Anomaly alerts are in beta and enabled per workspace. If your workspace does
  not show **Alerts** or the **Anomalies** tab, ask Unkey to enable the beta.
</Note>

Alerts apply only to production environments. Preview activity never creates alerts.

## Metrics Unkey monitors

Each alert covers one metric for one app and its production environment.

| Metric | What it means |
| --- | --- |
| 5xx errors | The server-error ratio rose above its recent level. |
| 4xx errors | The client-error ratio rose above its recent level. |
| Requests | Request volume rose above its recent level. |
| Request drop | Request volume fell far below a recent active level. |
| Egress | Outbound network traffic rose above its recent level. |
| CPU | CPU usage rose above its recent level. |
| Memory | Average memory use across instances reached 90%. |
| OOM killed | An instance was terminated for running out of memory. |
| Crash loop | An instance entered `CrashLoopBackOff`. |

An alert belongs to the app and environment, not to a single deployment. It keeps the active deployment as context and stays open across a redeploy, so you can see whether a rollout helped instead of getting a new alert for every deploy.

## How detection works

Unkey evaluates closed 5-minute windows and compares each one with up to 24 hours of history. It waits for a window to fully close before evaluating it, so normal telemetry delay doesn't look like a traffic drop. Unkey checks a window 5 minutes after it closes, so an event near the start of that window can be up to 10 minutes old by the time Unkey evaluates it, while an event near the end is closer to 5 minutes old. Confirmation windows and normal queueing delay can add more time on top of this.

If Unkey misses a scheduled check, the next one catches up on missed windows in order, up to 1 hour back. A longer gap resets the two-window confirmation that moderate error and request-drop alerts require.

Unkey installed anomaly detection's ClickHouse rollups by replaying 7 days of history, so apps that already existed at that point started with a full 24-hour baseline immediately. Only the single 5-minute window in progress during that installation was skipped. This replay was a one-time setup step, not something that repeats each time a workspace joins the beta. A newer app still needs to earn its own history: at least 1 hour before it can trigger a spike alert, and 6 hours before it can trigger a request-drop alert, measured from the app's creation time, not from zero.

Request, egress, and CPU spikes can open on a single unusual window. Moderate 4xx and 5xx increases, and request drops, need two consecutive windows to confirm.

For that baseline comparison, an error alert compares the percentage of failed requests to the baseline, and also requires at least 20 more failures than the baseline predicts. This keeps a large percentage swing in a small number of requests from triggering an alert.

A severe 5xx spike skips the baseline comparison entirely: if at least half of requests fail and there are at least 50 failures in one window, Unkey opens the alert on that window, without waiting for a second confirming window or the 20-failure baseline check above.

Unkey tracks how far data ingestion has progressed in each region a deployment runs in. Every region the deployment actually runs in must have ingested data through the window before Unkey evaluates it; only regions the deployment doesn't run in are excluded from this check. A delayed region keeps that window incomplete, and Unkey can't open or resolve an alert from an incomplete window, even if other regions are current. A recent watermark doesn't guarantee every data point has already arrived.

Instance failures are rare events. A single OOM or crash-loop report can open an alert on the window it's evaluated in, without waiting for a baseline or a second confirming window. When there is no such event, Unkey checks resource completeness to decide whether the window counts as clean for recovery.

A request-drop alert needs an active deployment with at least one running region. Unkey suppresses the alert if the deployment has no ID, is stopped, or has no running regions. Setting `autoscaling_replicas_min = 0` does not suppress it: the ability to scale to zero doesn't make an actual drop expected.

When a complete window has no requests, Unkey recalculates drop eligibility from the latest rolling values instead of reusing an earlier zero-request window's eligibility. Old buckets age out of the 12-bucket window Unkey uses for this calculation.

### Faster failure detection (opt-in beta)

Workspaces that opt in separately get 1-minute polling for `OOMKilled` and `CrashLoopBackOff` events, instead of waiting for the 5-minute cycle. The control plane stores each reported failure durably before acknowledging it, so this path doesn't depend on the same event buffer that feeds the health charts. A stored failure is normally processed on the next poll, but queueing, retries, and delivery delays can add time. This is not a guaranteed end-to-end delivery time.

This path opens alerts only for the active production deployment in a running region. A duplicate report never reopens a resolved alert. A new failure resets the recovery count, but resolving the alert still needs three complete quiet 5-minute windows, the same as every other metric. Other metrics keep their normal 5-minute cadence, and this path adds no email, Slack, or webhook notifications.

Health charts still read from ClickHouse event history, which is separate from this durable inbox. A failure alert can appear before its chart bar, or without a bar at all if that separate write is lost.

## Read the Anomalies tab

Open a project, select an app, and click **Anomalies**. Use the environment control to select the production environment.

The 7-day overview strip shows hourly behavior. Use the range selector for the last 24 hours, 6 hours, or 7 days in more detail, and switch between 5xx, 4xx, Requests, Egress, CPU, Memory, or Health.

The solid line is the observed value. The dashed line and shaded band show the expected baseline and its normal range. Requests also show a lower traffic boundary, and Memory shows a fixed 90% limit. The Health chart shows OOM and crash-loop events as bars.

The chart uses the same baseline and threshold calculations as the detector, so the expected band and boundaries reflect the same math. It needs 12 observed 5-minute buckets before it can show an expected band, and 72 buckets plus 9 active buckets out of the last 12 before it can show the request lower boundary. Error variation excludes buckets with no requests.

The chart doesn't reproduce every reason an alert did or didn't fire. It doesn't check region-by-region topology and watermark completeness, apply the two-window confirmation rule, or use the fixed baseline snapshot the detector locks in for recovery. Use the alert's own focus card, not the chart, to see exactly why the detector opened or resolved it.

Shaded regions mark every anomaly window. Markers on the line identify alerts for the selected metric. Toggle deployment markers to compare changes with rollouts, and drag across the chart to zoom in.

The alert list below the chart includes open and resolved alerts, loading 25 at a time. Click **Load more** for additional rows. Select an alert to open focus mode, which shows its status, metric, observed value, expected baseline, detection window, and deployment context, plus the resolution message for a resolved alert.

## Use the alerts inbox

Open **Alerts** in the workspace navigation to see open anomalies across every production app. The inbox does not include resolved alerts. Filter by metric or app, and use the sparkline on each row for quick context.

Select an alert to open its app, environment, metric, and time range in focus mode. Once the detector resolves the alert, it leaves the inbox, but its app-level link (`?alert=<id>`) still works.

## Understand alert resolution

Alerts are read-only. Unkey resolves them automatically and shows the reason in the alert details.

An alert resolves when its metric returns to the baseline captured when the alert opened, for three consecutive complete windows. Memory must fall below 85% to count as recovered. Unkey uses this fixed opening baseline rather than a rolling one, so a continuing incident can't satisfy recovery just because the rolling baseline has shifted to match it. A 5xx window with at least half of requests failing and at least 50 failures never counts as recovered, even inside the recovery range.

An alert can also stay open for at most 24 hours. If it hasn't recovered by then, Unkey closes it anyway with `Baseline adapted after 24 hours`. This is a maximum-open cap, not proof the new level is expected or has settled down: by that point the rolling baseline already reflects the last 24 hours regardless of the alert, so Unkey stops comparing against the original opening baseline and lets a later change from the current level open a fresh alert. This can happen after an expected, permanent change, such as traffic doubling, or after an unresolved problem that simply hasn't recovered yet.

A request-drop alert resolves with `Deployment stopped` when the deployment has no ID, is stopped, or has no running regions. The normal recovery message is `Metric returned to baseline for 3 consecutive windows`.

Deleting an app or environment resolves its open alerts with `Deployment stopped` before removing it. If Unkey finds an alert whose app or environment metadata is already gone, it resolves that alert on the next check.

Open a resolved alert through its Anomalies deep link (`?alert=<id>`) to see its **Resolved** status, resolution time, and resolution message.

## Know the beta limits

Anomaly alerts are evidence for investigation, not a diagnosis. A traffic or resource change can be expected for your workload.

This beta does not include:

- Notifications. Alerts, including 4xx alerts, don't send email, Slack, or webhook messages.
- Per-app mute controls.
- A sensitivity control in the dashboard.
- Seasonal baselines for daily or weekly patterns.
- Latency anomalies.
- Guaranteed capture of every OOM or crash-loop event. A brief failure can disappear before it reaches the control plane. For faster-path workspaces, an acknowledged failure is durable; other workspaces depend on an event buffer that can drop rows under load.
- Raw error and request counts. Error alerts store the ratio, while raw counts appear only in internal logs.
- Measured results at 1 million monitored groups. Current figures at that scale are extrapolated from testing at 100,000 groups.
- Automatic before-and-after deployment comparison.

To investigate an alert further, use [runtime logs](/observability/logs), [request details](/observability/requests), and [deployment metrics](/observability/metrics).
