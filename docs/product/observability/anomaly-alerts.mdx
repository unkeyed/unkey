Anomaly alerts identify behavior in an Unkey Deploy production app that differs
from its recent baseline or crosses a health limit. Use them to find traffic
changes, error spikes, resource pressure, and failed instances without setting
a fixed limit for every app.

<Note>
  Anomaly alerts are in beta and enabled per workspace. If your workspace does
  not show **Alerts** or the **Anomalies** tab, ask Unkey to enable the beta.
</Note>

Alerts apply only to production environments. Preview activity does not create
alerts.

## Understand detected metrics

Each alert identifies one metric for one app and production environment.

| Metric | What the alert means |
| --- | --- |
| 5xx errors | The server-error ratio increased above its recent level. |
| 4xx errors | The client-error ratio increased above its recent level. |
| Requests | Request volume increased above its recent level. |
| Request drop | Request volume stayed far below a recent active level. |
| Egress | Outbound network bytes increased above their recent level. |
| CPU | CPU seconds increased above their recent level. |
| Memory | Average memory utilization across instances reached 90%. |
| OOM killed | At least one instance was terminated because it ran out of memory. |
| Crash loop | At least one instance entered `CrashLoopBackOff`. |

An alert belongs to the app and environment, not one deployment. The alert
records the active deployment as context and stays open across a redeploy. This
lets you see whether a rollout helped without splitting one incident into
separate alerts.

## Understand the baseline

Unkey evaluates closed 5-minute windows and compares them with up to 24 hours of
earlier activity. It waits one full bucket before evaluating a window so normal
telemetry delivery lag does not look like missing traffic.

New apps need at least 1 hour of observed data before baseline-based metrics can
alert. Unkey counts only the time after the app first produced data. It does not
treat time before the app existed as zero. Request-drop detection needs 6 hours
because short test runs often end with expected silence.

Request, egress, and CPU spikes can open after one unusual window. Moderate 4xx
and 5xx error increases must continue for two windows. Request drops must also
continue for two windows. A severe 5xx window can open immediately when at least
half of requests fail and there are at least 50 failures.

Error alerts use the percentage of requests that failed. They also require at
least 20 more failures than the recent baseline predicts. This avoids an alert
when a large percentage change affects only a few requests.

Unkey does not evaluate a source until its telemetry is complete for the whole
window. An incomplete window cannot open or resolve an alert.

## Read the Anomalies tab

Open a project, select an app, and click **Anomalies**. Select the production
environment with the environment control.

The 7-day overview strip shows hourly behavior. Use the range selector to view
the last 24 hours, 6 hours, or 7 days in detail. Select 5xx, 4xx, Requests,
Egress, CPU, Memory, or Health to change the chart.

The solid line is the observed value. The dashed expected line and band show
the recent baseline and normal range for that bucket. Requests also show a
lower traffic boundary. Memory shows a fixed 90% limit. The Health chart shows
OOM and crash-loop events as bars.

Shaded regions mark all anomaly windows. Markers attached to the line identify
alerts for the selected metric. Toggle deployment markers to compare changes
with rollouts, and drag across the chart to zoom into a smaller time range.

Select an alert in the range list to open focus mode. The details card shows its
status, metric, observed value, expected baseline, detection window, deployment
context, and resolution details.

## Use the alerts inbox

Open **Alerts** in the workspace navigation to see anomalies across production
apps. Switch between **Open** and **Resolved** to filter by status. Each row
includes recent context and a sparkline.

Select an alert to open the affected app, environment, metric, and time range in
focus mode.

## Resolve an alert

An open alert tracks ongoing anomalous windows. When the metric returns to its
opening baseline for three consecutive complete windows, Unkey resolves it
automatically. Memory must fall below 85% for recovery. Unkey judges recovery
against the baseline captured when the alert opened, so a long incident cannot
become its own normal.

You can resolve an understood alert before automatic recovery:

1. Open the alert from the workspace inbox or app **Anomalies** tab.
2. Click **Resolve**.
3. Enter a message that explains why the alert can close.
4. Confirm the resolution.

The message is required and appears in the alert details. Unkey also records
the action in the audit log. Resolving an alert does not change your app or its
telemetry.

If a deployment is stopped, an open request-drop alert resolves with the message
`Deployment stopped`.

## Know the beta limits

Anomaly alerts provide evidence for investigation, not a diagnosis. A traffic
or resource change can be expected for your workload.

This beta does not include:

- Email, Slack, or webhook notifications.
- Per-app mute controls.
- A sensitivity control in the dashboard.
- Seasonal baselines for daily or weekly patterns.
- Latency anomalies.
- Per-region telemetry completeness.
- Automatic before-and-after deployment comparison.

Use [runtime logs](/observability/logs),
[request details](/observability/requests), and
[deployment metrics](/observability/metrics) to investigate the affected
window.
