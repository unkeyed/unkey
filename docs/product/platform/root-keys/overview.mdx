A root key is how you call the Unkey API and use the CLI. It belongs to one workspace and carries a list of permissions that decides what it can do.

A root key isn't one of the API keys you issue to your own users. You create and verify those through the API, using a root key. See [API Management concepts](/api-management/get-started/concepts).

Manage root keys under **Settings > Root Keys**. You need the [admin role](/platform/workspace/team) to create, edit, rotate, or delete them. Developers don't see the **Root Keys** tab.

## What a root key looks like

A root key starts with `unkey_`, followed by random characters. Like every key, it's shown to you only once (see [Key storage](/platform/security/key-storage)). You never pass a workspace ID with it, because the key already identifies your workspace.

A root key doesn't expire unless a rotation sets an expiry. It has no credit limit or rate limit of its own.

## Create a root key

<Steps titleSize="h3">
  <Step title="Open the dialog">
    Under **Settings > Root Keys**, click **New root key**. Name it after the service that will use it, for example "Vercel Production". Your users never see the name.
  </Step>
  <Step title="Select permissions">
    Pick the permissions the key needs. The dialog groups them by resource: API, Keys, Ratelimit, Permissions, Identities, Projects, Portals, Apps, GitHub, Environments, and Deployments. For keyspaces, projects, apps, and environments you can grant a permission on all of them or on one by ID. You need at least one permission. See [Root key permissions](/platform/root-keys/permissions).

    <Frame>
      <img src="/images/dashboard/platform--root-keys-overview--permissions.png" alt="New root key dialog with the permissions picker open, listing workspace permission groups and per-keyspace permissions" />
    </Frame>
  </Step>
  <Step title="Copy the key">
    Click **Create root key**. The key is shown once with a copy button. Store it in your secret manager before you close the dialog. You can't see it again, only rotate or replace it.
  </Step>
</Steps>

The audit log records who created the key and which permissions it got.

## Edit a root key

From the key's row menu, choose **Edit root key** to change the name or the permissions. Saving replaces all of the key's permissions with what's selected in the dialog, so check the whole list before you save. Changes take effect within about 10 seconds.

## Rotate a root key

Rotating gives you a new root key with the same name and permissions, and stops the old one after a grace period.

1. Choose **Rotate root key** from the row menu.
2. Pick a grace period: revoke immediately, 15 minutes, 1 hour, 6 hours, or 24 hours.
3. Copy the new key. It's shown once, like a new key.
4. Update your services before the grace period ends.

When the grace period ends, requests with the old key fail with `err:unkey:authorization:forbidden`. If the old key was already set to expire sooner, it stops at that earlier time.

Rotate on a schedule that fits your security policy, and right away if a key has been exposed. With "revoke immediately", the old key stops working as soon as the new one exists.

## Delete a root key

Choose **Delete root key** from the row menu and confirm. You can't undo this. Within about 10 seconds, requests with the key fail with `err:unkey:authentication:key_not_found`. The audit log records the deletion as `key.delete`. Delete keys for services you've retired instead of leaving them active.

## If a root key leaks

Rotate it with "revoke immediately" or delete it, then remove the secret from wherever it was exposed. The key keeps working until you do.

If a root key is pushed to a public GitHub repository, [GitHub secret scanning](/platform/security/github-secret-scanning) reports it and every member of the workspace gets an email saying where it was found.

We store root keys hashed, so we can't tell you what a leaked key was, only which key ID a request used. That's another reason to create one key per service.
