Every API endpoint needs a specific permission on your root key. Grant each key only the permissions its service needs, and use the error message to find a missing one.

## How a permission is written

A permission has three parts, `{resource}.{id}.{action}`. The id is either one resource's ID or `*` for every resource of that type.

```text
api.api_1234abcd.read_key
api.*.read_key
```

The first grants `read_key` on one keyspace. The second grants it on every keyspace. `*` is the only wildcard and always fills the whole id, so you can't match only some IDs, like those with a certain prefix. To cover some keyspaces but not all, grant one permission per keyspace.

[Permission reference](/platform/root-keys/permissions-legacy) lists every resource type and action, and whether the dashboard lets you limit it to one resource.

## Choose permissions

Grant the smallest set that lets the service do its job, and use one root key per service. That keeps the audit log clear and makes rotation easy. For example:

- A service that only verifies keys for one keyspace needs a single permission, `api.<keyspace ID>.verify_key`.
- A CI job that deploys needs `create_deployment` on its project or environment, and nothing about keys.

Keep `delete_api`, `delete_project`, and `delete_app` away from anything automated. [Delete protection](/platform/security/delete-protection) still blocks a key that holds them, but a key without them can't even try.

## When a permission is missing

Most endpoints accept any one of a short list of permissions, and a few need several at once. Without them, the request fails with `err:unkey:authorization:insufficient_permissions`. The `detail` field lists every permission that would have worked:

```text
Missing one of these permissions: api.*.delete_api or api.api_1234abcd.delete_api
```

Grant any one of them and the call succeeds.

Some endpoints also list a longer string like `unkey:v1:ws_123:projects/proj_123/apps/*#write`. You can't grant that form, so ignore it and grant one of the three-part permissions.

### A 404 can mean a missing permission

Some endpoints return `404` instead of `403` when a permission is missing, the same as if the resource didn't exist. That way a denied request can't reveal what's in your workspace. These include `apis.getApi`, `apis.listKeys`, `keys.createKey`, `identities.updateIdentity`, `permissions.getRole`, and `ratelimit.getOverride`. If an endpoint you expect to work returns a 404, check the root key's permissions. See [Insufficient permissions](/errors/unkey/authorization/insufficient_permissions).

## Permissions on your own keys are different

The permissions you attach to the API keys you issue to your users, and check with `keys.verifyKey`, have nothing to do with root key permissions. They're compared as exact strings, so `*` is an ordinary character there. A key permission named `documents.*` matches a check for exactly `documents.*` and doesn't grant `documents.read`. See [Authorization](/api-management/authorization/overview).
