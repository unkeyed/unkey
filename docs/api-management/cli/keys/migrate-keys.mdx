Move keys from a homegrown system into a keyspace with `unkey keys migrate`. You send hashes, not plaintext keys. Users keep the keys they already have, and your backend then calls `keys.verifyKey` instead of your own lookup. The steps, the SHA-256 base64 format, and what you stop maintaining are on [Migrating keys](/api-management/keys/migrating-keys).

<RootKeyPrereq />

The command imports the hashes under a migration ID from support, so the keys work with Unkey without being reissued. It returns `200` even when some keys fail. `data.migrated` lists each imported hash with its new `keyId`. `data.failed` lists the hashes that didn't import, usually because the hash already exists in Unkey. Hashes must be unique across all of Unkey, not just your workspace. Calls `POST /v2/keys.migrateKeys`.

## Usage

```bash
unkey keys migrate --api-id=<api id> --keys=<keys> --migration-id=<migration id> [flags]
```

## Flags

<ParamField body="--api-id" type="string" required>
  Id of the API to import the keys into.
</ParamField>

<ParamField body="--keys" type="string" required>
  JSON array of key objects. Only `hash` is required. Each object also takes `name`, `externalId`, `meta`, `roles`, `permissions`, `expires`, `enabled`, `credits`, and `ratelimits`, with the same meaning as on `unkey keys create`.
</ParamField>

<ParamField body="--migration-id" type="string" required>
  Id of the migration provider configured for your workspace. Unkey support issues it.
</ParamField>

## Required permissions

`api.*.create_key` or `api.<apiId>.create_key`. See [Root key permissions](/platform/root-keys/permissions).

## Examples

```bash Import two hashes
unkey keys migrate --migration-id=mig_1234abcd --api-id=api_1234abcd \
  --keys='[{"hash":"9f86d08...","externalId":"user_1"},{"hash":"e3b0c44..."}]'
```

Or send the whole request as JSON:

```bash Raw body
unkey keys migrate --body='{"migrationId":"mig_1234abcd","apiId":"api_1234abcd","keys":[{"hash":"9f86d08...","externalId":"user_1"}]}'
```
