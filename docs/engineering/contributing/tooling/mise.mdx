## What mise owns

Unkey uses mise to select project tools and run repository tasks. The source of
truth is `.mise/config.toml`, `.mise/mise.lock`, and `.mise/tasks/*`.

Use mise for local repository commands:

```bash
mise run build
mise run test
mise run fmt
mise exec -- rask ./pkg/cache
```

Do not use Makefiles for repository workflows. They are legacy and can drift
from the pinned toolchain.

## Install the toolchain

Install the pinned mise binary, then install the tools from `.mise/config.toml`:

```bash
./dev/install-mise
mise install --locked --yes
```

<Note>
  If you run into github ratelimit issues, mise can use an auth token to get higher limits
  You can manually create a token, or use the one from your `gh` cli:

  ```bash
  GITHUB_TOKEN=$(gh auth token) mise install
  ```

</Note>

`mise install` installs languages, CLIs, and package managers. It does not run
repository setup tasks. Repository tasks declare setup work as dependencies, so
you don't need to run setup-only tasks manually.

## How tools are pinned

Add tools to the `[tools]` section in `.mise/config.toml`. Pin exact versions instead
of floating versions like `latest`.

```toml
[tools]
node = "24.19.0"
"github:pnpm/pnpm" = "11.5.0"
"github:depot/cli" = "2.101.67"
```

After changing tools, update `.mise/mise.lock`. Disable locked mode only for
this maintenance command, not for installation or CI:

```bash
MISE_LOCKED=0 mise lock <tool>
```

Use the backend-qualified name when needed, for example:

```bash
MISE_LOCKED=0 mise lock github:pnpm/pnpm
MISE_LOCKED=0 mise lock github:depot/cli
```

Keep lock entries for Linux and macOS on both x64 and ARM64:

```bash
MISE_LOCKED=0 mise lock <tool> --platform linux-x64,linux-arm64,macos-x64,macos-arm64
```

Verify `mise install --locked --yes` with an empty tool directory on each
supported platform. A warm installation does not exercise archive downloads or
checksum verification.

Keep `go.mod`'s minimum Go version and `web/package.json`'s Node compatibility
range. Update `packageManager` alongside mise's pnpm pin. Go uses
`GOTOOLCHAIN=local`, and pnpm uses `pmOnFail: error`, so neither silently downloads
a replacement toolchain. Module and package dependencies retain their native
lockfiles. OS packages and container base images remain separate pins.

## CI setup and caching

Workflows use `.depot/actions/setup-mise` after checkout. Every job installs the
full locked toolchain and shares the same tool cache for its platform and event
type. Setup restores Go and pnpm caches but does not install project dependencies.
Tasks own dependency installation. For example, `build-web`, `test-web`, and
`fmt` depend on `install-web`.
Execute project commands with `mise run` or `mise exec`; installation alone does
not select tools for subsequent steps.

The action caches installed tools by OS, architecture, OS/libc identity, event
type, and bootstrap/config/lock contents. Go module/build caches
and the pnpm store have separate keys. Restoring a cache never skips the locked
installation check. CI must not regenerate lockfiles or upgrade tools.

Depot runners still supply the Docker daemon, Buildx, Compose, and OS packages.
Go and web integration tests need Docker access. Installing mise tools does not
replace those runner capabilities.

## Build containers

Go builders and the portal builder copy `dev/install-mise` and both mise files
before application source. Docker reuses the installation layer when only source
changes. Go module/build caches and the portal's pnpm store use separate BuildKit
cache mounts. Runtime images contain the built application, not mise.

The eBPF generator retains its digest-pinned Ubuntu base, clang/LLVM 18, and
forced `linux/amd64` platform. Mise supplies Go from the repository lockfile.
`mise run generate-bpf` mounts the source separately from installed tools and
caches Go downloads/builds under `${XDG_CACHE_HOME:-$HOME/.cache}/unkey-bpf`.
CI also caches the generator image with BuildKit. After toolchain changes, test
a cold build and a cached build and confirm that generated `.go` and `.o` files
have no unexpected differences. The Ubuntu digest does not freeze apt package
revisions, so changes to those packages need the same reproducibility check.

## How tasks work

Repository tasks are executable files under `.mise/tasks/`. The file name is the
task name. Metadata is declared with `#MISE` comments near the top of the file.

```bash .mise/tasks/example
#!/usr/bin/env bash
#MISE description="Run an example workflow"
#MISE depends=["setup-example"]
set -euo pipefail

example-tool run
```

Use task dependencies for setup work. If a task needs another task to prepare
inputs or local state, add `#MISE depends=["task-name"]` instead of telling
users to run setup steps by hand.

## Hidden dependency tasks

Some tasks exist only to prepare other tasks. Mark those tasks hidden:

```bash
#MISE hide=true
```

Hidden tasks can still run as dependencies. Use them for setup work that users
usually don't need to invoke directly.

You can inspect hidden tasks when debugging:

```bash
mise tasks --hidden
mise tasks deps <task>
```

## Cache task outputs

Tasks can declare source and output files. Mise skips the task when all outputs
are newer than the sources.

```bash
#MISE sources=["path/to/input.json"]
#MISE outputs=["path/to/output"]
```

Use this for expensive setup steps with clear inputs and outputs. Do not add
outputs for tasks that must always run, such as tests or formatters.

## Add a task

When you add a task, follow this checklist:

1. Create an executable script in `.mise/tasks/<name>`.
2. Add a clear `#MISE description`.
3. Add `set -euo pipefail` for Bash tasks.
4. Add `#MISE depends=["task-name"]` when the task has setup dependencies.
5. Add `#MISE sources` and `#MISE outputs` only when skip behavior is safe.
6. Mark setup-only tasks with `#MISE hide=true`.
7. Run `mise tasks validate`.
8. Run the smallest task or command that proves the task works.

Prefer a task when the command is part of a repeated repository workflow. Use
`mise exec -- <tool>` for one-off direct tool calls.

## What to expect

Mise tasks run from the repository root unless configured otherwise. Keep task
scripts explicit about paths, for example `pnpm --dir=web` instead of changing
directories for the rest of the script.

Task dependencies run before the requested task. Hidden tasks can still run as
dependencies. `mise tasks` hides them by default, and `mise tasks --hidden`
shows them.

The lockfile is part of the review surface. If `.mise/config.toml` changes, expect a
matching `.mise/mise.lock` change unless the edit only affects task configuration or
environment variables.
