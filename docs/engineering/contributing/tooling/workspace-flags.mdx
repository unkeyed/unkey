---
title: "Workspace flags"
description: "MySQL storage for boolean platform features and workspace overrides."
---

Workspace flags store boolean platform feature settings in MySQL. They are
separate from [Vercel feature flags](/contributing/tooling/feature-flags), which
remain the dashboard's frontend flag system.

The dashboard loads flags with the current workspace. There are no dedicated
flag API routes, settings page, or automatic registration. Customer-facing
interfaces use the term platform features.

## Store definitions and overrides

The schema lives in `web/internal/db/src/schema/flags.ts`.

| Table | Fields | Constraint |
| --- | --- | --- |
| `flags` | `id`, `slug`, `description`, `default_value`, `allow_opt_in`, `allow_opt_out` | Unique, case-sensitive `slug` |
| `workspace_flag_overrides` | `workspace_id`, `flag_id`, `value` | Unique workspace and flag pair |

Both tables also have an internal `pk` column. Defaults and overrides use
non-null boolean columns. There is no type column, environment dimension, or
separate opt-in value.

An override row determines the effective value, including an explicit `false`.
Without a row, the workspace inherits `default_value`. Deleting an override
restores inheritance, which can enable a feature whose default is `true`.

Definitions are operator-managed records. Provision them through the approved
database change process with a boolean default. Treat published slugs as stable.

## Read flags in the dashboard

The existing `workspace.getCurrent` tRPC procedure loads effective flag values
from MySQL and includes them in `workspace.flags`, keyed by slug. Both the
preloaded-context path and the fallback workspace lookup include flags.

The flag query left-joins all definitions to overrides for the resolved
workspace ID. An explicit `false` overrides a `true` default. Missing overrides
inherit the default, and an empty definition table produces an empty map.

Consumers access the values through the existing workspace provider:

```tsx
const { workspace } = useWorkspace();
const previewEnabled = workspace?.flags["deployment-preview"] ?? false;
```

This adds one database query to `workspace.getCurrent`, not to every tRPC context
creation. It adds no separate browser request. Flag lookup failures fail the
workspace request rather than silently returning an empty map. Apply the flag
schema before deploying the updated workspace loader.

## Use the database queries

The queries in `pkg/db/queries/` provide the data-access operations without
exposing an HTTP interface.

- `ListFlags` left-joins definitions to one workspace's overrides and sorts by
  slug. Its nullable override value distinguishes absence from `false`.
- `FindFlagBySlug` locks the definition with `FOR UPDATE`. Use it within a
  transaction when checking policy before writing an override.
- `UpsertWorkspaceFlagOverride` inserts or replaces one workspace's value.
- `DeleteWorkspaceFlagOverride` removes one workspace's override and is
  idempotent when the row is absent.

The `allow_opt_in` and `allow_opt_out` columns default to `false`. These are
stored policy fields, not database-enforced permissions. Future consumers must
authenticate workspace access and enforce the applicable policy before writes.
