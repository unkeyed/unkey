title: "Feature flags"
description: "How feature flags work in the dashboard and Ctrl"
---

Flags are declared in `web/apps/dashboard/lib/flags/index.ts`. The `identify` helper reads the current session and passes stable `user.id` and `team.id` entities to each flag, so targeting by user or organization doesn't need extra wiring per flag. `team.id` is the WorkOS organization ID, which the database stores as `workspaces.org_id`. It isn't the Unkey workspace ID.

The flag registry uses a local adapter wrapper instead of calling `vercelAdapter()` directly. When the Vercel `FLAGS` setup is present, the wrapper returns the Vercel adapter. When `FLAGS` is absent, it returns a noop adapter that resolves each flag to its declared `defaultValue`.

## Adding a flag

From `web/apps/dashboard`:

```bash
vercel flags create my-flag --kind boolean --description "What it gates"
```

Declare it alongside the existing ones:

```ts
export const myFlag = flag<boolean, Entities>({
  key: "my-flag",
  description: "Gates the new dashboard workflow",
  defaultValue: false,
  options: [
    { value: false, label: "Off" },
    { value: true, label: "On" },
  ],
  identify,
  adapter: adapter(),
});
```

Every flag must declare a `defaultValue`. The noop adapter uses that value in local development and self-hosted environments that don't configure Vercel Flags.

Add the flag to `web/apps/dashboard/lib/flags/resolve.ts` so the `FlagsProvider` in the root layout exposes it to client components:

```ts
export async function resolveAll() {
  const [helloWorld, myFlag] = await Promise.all([flags.helloWorld(), flags.myFlag()]);
  return { helloWorld, myFlag };
}
```

The `Flags` type is derived from `resolveAll`'s return shape, so any flag missing from this list will fail to type-check at every `useFlag(key)` call site.

Use it from a client component:

```tsx
import { useFlag } from "@/lib/flags/provider";

const enabled = useFlag("myFlag");
```

Or from server code by awaiting the flag directly:

```ts
import { myFlag } from "@/lib/flags";

const enabled = await myFlag();
```

## Toggling

From the Vercel dashboard, or from the CLI:

```bash
vercel flags enable my-flag development
vercel flags disable my-flag development
```

In dev, the Vercel Toolbar appears in the bottom-right. You can override a flag locally there, but flipping the switch alone does nothing. You have to click **Apply** for the override to write its cookie and reload the page.

## Self-hosted dashboards

Self-hosted dashboards can import `@/lib/flags` without configuring Vercel Flags. If `FLAGS` is missing, the adapter wrapper logs a warning and evaluates flags through the noop adapter.

The noop adapter doesn't contact Vercel, doesn't report flag values, and doesn't load remote targeting rules. It returns each flag's `defaultValue`, so choose safe defaults before using a flag in a self-hosted path.

## Ctrl

Ctrl evaluates flags through an isolated OpenFeature API that `featureflag.NewFromConfig` in `pkg/featureflag` builds from a `featureflag.Config`. It starts the backend's background refresh on the service's runner and shuts the API down with it. Application code depends only on the OpenFeature client. Each backend is an OpenFeature provider in its own package: `pkg/featureflag/static` and `pkg/featureflag/vercel`. Flag keys live in `pkg/featureflag/flags.go`. An empty provider uses the OpenFeature SDK's built-in no-op provider. To add a backend, add a provider package and a case in `NewFromConfig`. The ctrl worker config selects the provider:

```toml
[feature_flags]
# "" (default): every flag returns its code default, with no network access.
# "static": local development and tests only.
# "vercel": polls the Vercel Flags datafile.
provider = "static"

[feature_flags.static]
private-networking = true

[feature_flags.vercel]
sdk_key = "${VERCEL_FLAGS_SDK_KEY}"
# refresh_interval = "1m"
# http_timeout = "10s"
# max_staleness = "10m"
```

`sdk_key` is the bare server SDK key for one Vercel environment, starting with `vf_server_`. It isn't the `FLAGS` connection string that the dashboard reads. The provider doesn't send an environment header, so the key selects the environment.

The static provider returns the listed value for every workspace. A flag missing from `feature_flags.static` is an evaluation error, not `false`. Restart the worker to apply config changes.

Ctrl sends only `team.id`, set to `workspaces.org_id`, so dashboard targeting by organization applies to Ctrl too. Infrastructure decisions never use a user identity.

The Vercel provider in `pkg/featureflag/vercel` supports a subset of Vercel Flags: boolean variants, direct targets, a paused flag, and a fixed fallthrough variant. A flag that uses rules, splits, experiments, or environment reuse returns a parse error instead of a value. The provider keeps the last good datafile for up to `max_staleness` while refreshes fail. After that, and before the first successful refresh, evaluations return `PROVIDER_NOT_READY`. A service using it exports `unkey_feature_flags_ready`, `unkey_feature_flags_snapshot_age_seconds`, and `unkey_feature_flags_refresh_failures_total`.

### Private networking

Ctrl reads `private-networking` once, when it creates a deployment, and stores the answer as `private_networking` in `deployments.capabilities`. Create evaluates the flag inside the journaled step that builds the deployment payload, after the plan, spend, and runtime checks. Only workspaces with an app binding to another app are evaluated. If a row already exists under the same deployment ID, for example when an approval starts a deployment its push created, Create reuses the stored decision without evaluating the flag. A rebuild gets a new deployment ID and evaluates again. Other deployments store it as off without a flag lookup. A deployment stored as off also gets no binding variables, because their hostnames resolve only through private DNS.

Krane, discovery, and the resolver read the stored value, never the flag. Every region configures the same DNS for a deployment, and a later flag change or flag outage doesn't rewrite DNS for running deployments. To apply a changed flag to an app, redeploy it.

A flag evaluation error fails the payload step, and Restate retries it. If the retries fail, the create fails without writing a row. `unkey_control_feature_flag_evaluations_total{flag, result}` counts evaluations by result.

### Deployment capabilities

`deployments.capabilities` is a JSON object with the capabilities decided once when Ctrl creates a deployment. In Go it's `DeploymentCapabilities` in `pkg/mysql/types`. A missing key is off, so rows written before a key existed keep it off. Create writes the whole object in the deployment payload step, and an approval reuses the whole object from the existing row.

To add a capability that must not change for a running deployment, add a field to `DeploymentCapabilities` and the `DeploymentCapabilities` TypeScript type, then decide it in `decideCapabilities` in `svc/ctrl/worker/deploy/capabilities.go`. SQL filters on a capability with `JSON_CONTAINS(capabilities, 'true', '$.<key>')`. A flag that only changes behavior at request time doesn't belong here.

#### Roll out the column

Apply the schema change that adds `deployments.capabilities` before you deploy binaries that read it. Ctrl and the API select the column and Ctrl inserts it, so an older schema fails those queries.

The column defaults to `{}`, and nothing backfills it. Deployments that used private networking before the column existed switch to cluster DNS at their next reconcile. Redeploy them with the flag on, or set their capabilities explicitly as a reviewed migration.
