---

Deploy anomaly alerts depend on Kubernetes cron delivery, Restate execution,
ClickHouse completeness, and MySQL persistence. Diagnose those layers in that
order. Do not edit Restate state or change `alert_events.status` to hide a
failing detector.

The [architecture page](/architecture/services/control-plane/worker/deploy-anomaly-detection)
defines the pipeline. The
[detector math](/architecture/services/control-plane/worker/deploy-anomaly-detection-math)
defines every expected threshold.

## Identify the expected window

Calculate the window that a cron tick must evaluate. All values are UTC Unix
seconds.

```bash
now=$(date -u +%s)
window_start=$((now / 300 * 300 - 600))
window_end=$((window_start + 300))
window_start_ms=$((window_start * 1000))
cron_key="deploy-anomaly-${window_start}"

printf 'window=[%s, %s) key=%s\n' \
  "$(date -u -d "@${window_start}" --iso-8601=seconds)" \
  "$(date -u -d "@${window_end}" --iso-8601=seconds)" \
  "${cron_key}"
```

Use the exact window in logs, Restate invocations, and ClickHouse watermark
comparisons. A later cron key does not prove that an earlier window completed.
The expected window ended at least 5 minutes ago. The handler returns a no-op
when `window_end > now - 5 minutes`, even if a caller constructs a newer key.

## Diagnose a cron that is not firing

The first symptom is no `RunDeployAnomalyCheck` invocation for the expected
key. Check Kubernetes before the worker.

1. Confirm that the CronJob exists and uses `*/5 * * * *`.

   ```bash
   kubectl -n unkey get cronjob restate-deploy-anomaly
   kubectl -n unkey describe cronjob restate-deploy-anomaly
   ```

2. Inspect its latest jobs and caller logs.

   ```bash
   job_name=$(
     kubectl -n unkey get jobs \
       --sort-by=.metadata.creationTimestamp \
       -o custom-columns=NAME:.metadata.name \
       --no-headers |
       awk '/^restate-deploy-anomaly-/ { latest = $0 } END { print latest }'
   )
   kubectl -n unkey logs "job/${job_name}" --all-containers
   ```

3. Confirm that the request path contains the expected cron key and handler:
   `hydra.v1.CronService/<cron_key>/RunDeployAnomalyCheck/send`.
4. Confirm that Restate ingress and the control-plane worker are ready.
5. Compare the local chart entry in
   `dev/k8s/charts/restate-cronjobs/values.yaml` with the production
   `deploy-anomaly-check` job in the `unkeyed/infra` repository at
   `eks-cluster/helm-chart/restate/environments/{canary,production001}/us-east-1.yaml`.

After configuring the Restate CLI for the affected cluster, inspect the exact
cron object:

```bash
restate invocations list \
  --service hydra.v1.CronService \
  --key "${cron_key}"
```

Use `restate invocations describe <invocation_id>` to inspect the journal. A
cron invocation that reaches its maximum attempts must be killed by its retry
policy, not paused. If it is paused, correct the deployed retry configuration
before relying on later ticks.

Do not manually invoke production to test a fix without separate operational
approval. A manual call creates shared state and can overlap scheduled work.

## Diagnose incomplete windows

Start with the structured warning from shard 0. It emits one warning per
incomplete source and window with `source`, `region`, `watermark`, and
`window_end`. The source values are `requests` and `resources`. Compare the
named region's watermark with `window_end`.

`GetAnomalySourceWatermarks` reads `{Source, Region, Watermark}` rows from
`anomaly_source_watermarks_v1`. Inspect every region directly:

```sql
SELECT
  source,
  region,
  toInt64(
    toUnixTimestamp(
      if(
        source = 'resources',
        max(time) + INTERVAL 1 MINUTE,
        max(time) + INTERVAL 5 MINUTE
      )
    )
  ) * 1000 AS watermark
FROM default.anomaly_source_watermarks_v1
WHERE time > now() - INTERVAL 2 HOUR
GROUP BY source, region
ORDER BY source, region;
```

A region is active for a source when its latest ingest is within the last 2
hours. For each source, compare the minimum watermark across active regions
with the expected window end. Every active region must have reached the end. A
source with no active region is incomplete. A region with no ingest for more
than 2 hours is inactive and does not block detection.

The table is keyed by `(source, region)` and receives rows through materialized
views on these raw sources:

| Source | Raw table |
| --- | --- |
| `requests` | `frontline_requests_raw_v1` |
| `resources` | `instance_checkpoints_v1` |

Confirm the complete detector object set after a migration:

```sql
SHOW TABLES FROM default LIKE 'anomaly_%watermark%';
SHOW TABLES FROM default LIKE 'frontline_requests_anomaly_%';
SHOW TABLES FROM default LIKE 'instance_resources_container_%';
```

The combined results must contain these seven objects:

- `anomaly_requests_watermark_mv_v1`
- `anomaly_resources_watermark_mv_v1`
- `anomaly_source_watermarks_v1`
- `frontline_requests_anomaly_per_5m_mv_v1`
- `frontline_requests_anomaly_per_5m_v1`
- `instance_resources_container_per_5m_mv_v1`
- `instance_resources_container_per_5m_v1`

There is no instance-event watermark materialized view.

Inspect the producer and materialized view for the delayed pair. If a region is
unexpectedly inactive, check why it has produced no ingest for 2 hours. Do not
reinterpret `INCOMPLETE` as `ZERO_COMPLETE`. An incomplete metric cannot open,
advance, touch, or resolve an alert.

Instance-event completeness is different because OOM and crash-loop rows are
sparse. A row in `instance_events_raw_v1` is actionable even when the resources
watermark is incomplete. When no event row exists, the resources source
watermark decides whether the zero is complete. The ctrl API instance-event
buffer uses `Drop: true`. If a known lifecycle event has no raw row, inspect
buffer pressure and flush errors. A dropped event causes a missed alert. It
does not create a stuck incomplete source.

## Diagnose a failed shard or child

The cron fans out to 16 shard virtual objects by default. For an expected shard,
build the key and inspect its invocation.

```bash
shard=0
shard_count=16
shard_key="${window_start_ms}/${shard}/${shard_count}"
previous_window_start_ms=$((window_start_ms - 300000))
previous_shard_key="${previous_window_start_ms}/${shard}/${shard_count}"

restate invocations list \
  --service hydra.v1.DeployAnomalyShardService \
  --key "${shard_key}"

restate invocations list \
  --service hydra.v1.DeployAnomalyShardService \
  --key "${previous_shard_key}"

restate kv get hydra.v1.DeployAnomalyShardService \
  "${shard_key}"

restate kv get hydra.v1.DeployAnomalyShardService \
  "${previous_shard_key}"
```

Before the current shard queries or dispatches, it calls the prior key's
exclusive `EvaluateShard` handler. If the predecessor finished, it returns its
stored result without querying ClickHouse or MySQL. If it is running, the
current shard waits. If it never ran, it evaluates and first calls its own
predecessor.

The recursive chase is limited to 12 predecessors. Confirm chronological
execution and catch-up across gaps of at most 1 hour. A predecessor beyond that
limit counts as absent, and the current shard proceeds. A longer outage
restarts consecutive-window candidate evidence. The group object's
`last_window_end` guard still rejects duplicate or stale evaluations.

`EvaluateShard` retries are bounded. Exhaustion must kill the invocation. A
paused invocation would wedge the chain because a later predecessor call queues
behind it.

For the current shard, look for journal failures in watermark reads, candidate
queries, batched MySQL metadata resolution, and per-group calls. Metadata
batches contain at most 500 groups. The parent awaits every child. Any failed
child withholds the heartbeat even if other groups succeed.

Metadata resolution also identifies open-alert groups whose app or environment
no longer exists. The shard resolves each orphaned batch of at most 500 groups
with `Deployment stopped`. Inspect that batched resolution step when a deleted
group remains open.

Inspect the shard object's evaluated marker, stored dispatched and pending
counts, and `pending_groups` keys. Compare the key count with `groups_pending`.
A repeat call must return these stored results without new ClickHouse or MySQL
steps. The next window receives the pending keys from its predecessor's
`EvaluateShard` result.

`ListOpenAlertEventGroups` reads all `status = 'open'` groups through the plain
`status_idx` index. Every shard repeats this small, cheap MySQL scan and keeps
rows where `city.CH64(workspace_id) % shardCount == shard`. That result must
match ClickHouse `cityHash64(workspace_id) % shard_count`. Use these known
vectors when diagnosing a hash mismatch:

| Workspace ID | CityHash64 |
| --- | ---: |
| `ws_test` | `14195424828609858884` |
| `ws_local` | `6295136450341388082` |

For one group, use its stable evaluator key:

```bash
workspace_id="ws_XXX"
app_id="app_XXX"
environment_id="env_XXX"
group_key="${workspace_id}/${app_id}/${environment_id}"

restate invocations list \
  --service hydra.v1.DeployAnomalyService \
  --key "${group_key}"
restate kv get hydra.v1.DeployAnomalyService "${group_key}"
```

Expected state keys are `candidate:<metric>`, `candidate_window:<metric>`,
`open_alert:<metric>`, `fired_at:<metric>`, `quiet:<metric>`,
`snapshot:<metric>`, and `open_alerts_reconciled`, plus the group-level
`last_window_end`.

The evaluator does not persist a prior detector `Input`. For a `ZERO_COMPLETE`
request window, inspect the current rolling median and active-bucket count in
the request payload. Those fresh values must clear request-drop eligibility
when an old active bucket leaves the preceding 12 buckets. A reconciled open
request-drop alert retains its metric identity and still resolves at the
24-hour maximum duration.

Compare the requested `window_end` with `last_window_end`. The evaluator returns
a strict no-op when the requested end is equal to or older than the stored end.
The warning `deploy anomaly window skipped because it is not newer` includes
both fields. A delayed old invocation must not change current state.

Treat MySQL as the customer-facing source of truth and Restate as detector
execution state. Do not use `restate kv edit` during diagnosis. A state edit can
break the one-open-alert invariant or discard the opening recovery snapshot.

## Investigate a false positive

Start with the stored alert. It preserves the observed ratio and baseline values
used when the detector opened. Raw error and request counts exist only in the
structured opening log.

```sql
SELECT
  id,
  workspace_id,
  project_id,
  app_id,
  environment_id,
  deployment_id,
  metric,
  status,
  fired_at,
  last_seen_at,
  window_start,
  window_end,
  observed_value,
  baseline_mean,
  baseline_stddev,
  threshold_sigma,
  resolved_at,
  resolution_message
FROM alert_events
WHERE id = 'alert_XXX';
```

Find the `deploy anomaly alert opened` log for the ID. Record these structured
fields before recalculating the rule:

- `alert_id`
- `metric`
- `current`
- `baseline_mean`
- `baseline_stddev`
- `observed_buckets`
- `baseline_window_buckets`
- `lifetime_start`
- `sigma`
- `threshold`

Use `window_start` and `window_end` to query the metric source. Confirm all of
these conditions:

1. At least one region was active for the request or resource source, and every
   active region had reached the window end. For a lifecycle event row, confirm
   that the detector treated it as actionable without a separate event
   watermark.
2. The environment was production.
3. ClickHouse grouping removed deployment identity but retained the correct
   workspace, project, app, and environment.
4. `lifetime_start` matches the app's MySQL `created_at` value aligned down to 5
   minutes, but is no earlier than the 24-hour lookback boundary.
5. Error alerts used a ratio and at least 20 excess failures.
6. Request drops had 72 observed baseline buckets, nine active recent buckets,
   at least 200 lost requests, a `deployment_id` whose deployment was not marked
   `stopped`, and at least one topology region with
   `desired_status = 'running'`.
7. The applied sensitivity and typed dashboard threshold mirror match the
   [detector math](/architecture/services/control-plane/worker/deploy-anomaly-detection-math).
8. The ClickHouse candidate filter used the minimum spike threshold across
   every lifetime from `max(observed_buckets, 1)` through 288, multiplied by
   `(1 - 1e-12)`. This rounding tolerance may over-include but must not exclude
   a Go anomaly. Run
   `TestAnomalyCandidateFilterToleratesFloat64Cancellation` after changing this
   filter.
9. An older app received its backfilled baseline. If it did not, confirm that
   the deploy anomaly migration in `pkg/clickhouse/migrations` completed for
   `anomaly_source_watermarks_v1`,
   `frontline_requests_anomaly_per_5m_v1`, and
   `instance_resources_container_per_5m_v1`.

Each 7-day backfill runs over closed buckets before its materialized view is
created. At most, the in-progress 5-minute bucket at migration time can be
absent. Apply the migration once in this order. The `NOT IN` replay guard is
race-free during the initial migration because the matching materialized view
does not exist yet.

Do not let a migration applier or operator rerun a backfill statement after its
materialized view exists while ingest continues. A source key that arrives
between the guard snapshot and insert can be counted by both paths. Stop ingest
for the rerun or deduplicate the affected rollup keys. Investigate migration
completion instead of inserting replacement rows without a deduplication plan.

### Investigate zero CPU or egress

The resource materialized view must read raw `instance_checkpoints_v1` rows and
preserve per-container counter bounds for each 5-minute bucket. Inspect its
definition:

```sql
SHOW CREATE TABLE default.instance_resources_container_per_5m_mv_v1;
```

The definition must select from `instance_checkpoints_v1` and aggregate
`cpu_usage_usec_min`, `cpu_usage_usec_max`,
`network_egress_public_bytes_min`, and
`network_egress_public_bytes_max`. The detector calculates a non-negative
`max - min` per container before summing containers to the app.

Do not restore a materialized view chained from a per-minute table. A live
insert block can contain one 5-second sample. Computing a delta inside that
block makes its minimum and maximum equal, which writes zero CPU and egress for
live traffic.

If detector values are correct but the dashboard differs, inspect
`instance_resources_per_minute_v1`. Dashboard CPU and egress calculate
non-negative per-container deltas in each 5-minute bucket, then sum those app
values for hourly points. Dashboard memory instead reads
`instance_resources_container_per_5m_v1`, divides `utilization_sum` by
`utilization_samples` per container, averages container values into instances,
and averages instances into the app. Hourly memory is the average of 5-minute
app values.

Do not compare an open alert with the latest rolling baseline. Recovery uses
the snapshot stored when the alert opened.

## Respond to an alert storm

An alert storm is a sudden increase in open rows across many independent groups.
Measure its scope before changing thresholds.

```sql
SELECT metric, COUNT(*) AS open_count
FROM alert_events
WHERE status = 'open'
GROUP BY metric
ORDER BY open_count DESC;
```

Group affected rows by workspace, environment, and 5-minute `window_start`.
Then compare the result with source watermarks and platform incidents.

- One metric and one source: inspect that telemetry producer and query change.
- Many metrics in one region: inspect regional ingestion and workload health.
- Request drops after a control-plane action: verify the `deployment_id`,
  `deployments.desired_state`, and `deployment_topology.desired_status` rows.
  The rule is suppressed when every topology region is stopped, but not only
  because `autoscaling_replicas_min = 0`.
- Alerts immediately after a sensitivity change: restore code and dashboard
  constants to the last reviewed values through the normal deployment process.

Do not change alert status rows before correcting the cause. That hides active
rows but does not correct candidate generation or future windows. Notifications
are not part of this phase, so stopping an email, Slack, or webhook integration
cannot stop detector writes.

## Diagnose an alert that stays open

Alerts are read-only in the dashboard. The detector closes an alert at the first
complete evaluation after it has been open for 24 hours.

`DefaultConfig` decodes `maxOpenDurationSeconds = 86400` as a 24-hour
`Config.MaxOpenDuration`. If a row remains open past that limit:

1. Compare `fired_at` plus 24 hours with the latest selected window end.
2. Confirm that the metric's request or resource watermark reached that window
   end. An absent OOM or crash-loop row uses the resources watermark. An
   `INCOMPLETE` input is a strict no-op and cannot resolve the alert.
3. Inspect the group virtual object for `open_alert:<metric>` and its latest
   invocation for a failed MySQL resolution step.
4. Confirm that the deployed `Config.MaxOpenDuration` is 24 hours.

If the app or environment was deleted, inspect its deletion workflow first. It
must durably resolve open alerts with `Deployment stopped` before deleting the
metadata. If deletion completed without that transition, inspect the next shard
run. Its batched orphan reconciliation must resolve any remaining open group
whose app or environment cannot be found.

Do not update MySQL or Restate state to close the alert. Correct the failed
evaluation path and let the detector persist the transition.

Use `resolution_message` to interpret a resolved row:

| Message | Meaning |
| --- | --- |
| `Metric returned to baseline for 3 consecutive windows` | Three complete windows crossed the recovery threshold captured when the alert opened. |
| `Deployment stopped` | A request-drop alert closed because its deployment stopped, or an app or environment deletion resolved the alert. Shard reconciliation uses the same message for orphaned metadata. |
| `Baseline adapted after 24 hours` | The alert stayed open for 24 hours, so the rolling baseline now represents the new level. |

The last message describes baseline adaptation, not proof that the new level is
healthy. Continue the incident investigation when the behavior is unexpected.

## Change sensitivity

Sensitivity is code-configured in this phase. There is no per-app sensitivity
UI. `DefaultConfig` uses `SensitivityNormal`, where `k = 4`. Low sensitivity
uses 5, and high sensitivity uses 3.

`svc/ctrl/worker/cron/deployanomaly/thresholds.json` is the canonical source for
the complete production rule inventory. The Go decoder calls
`DisallowUnknownFields` and rejects trailing JSON values. Configuration loading
uses per-value range checks and the cross-field invariants listed in the
[detector math](/architecture/services/control-plane/worker/deploy-anomaly-detection-math),
including duration safety, recovery ordering, finite positive sigma values, and
non-finite number rejection. An invalid embedded file causes a clear panic
during package initialization.

The dashboard stores one complete typed `deployAnomalyThresholds` mirror in
`web/internal/clickhouse/src/alert-thresholds.ts`. Its strict
`alert-thresholds-contract.test.ts` strictly parses the JSON and uses `toEqual`
for full deep equality. A mutation test proves that a nested difference fails.

To change the selected `Sensitivity`, update the detector call sites together
and keep the dashboard's displayed sigma consistent. To change a production
threshold:

1. Edit `svc/ctrl/worker/cron/deployanomaly/thresholds.json`.
2. Run the Go package tests, including
   `TestDefaultConfigMatchesSharedThresholds`.

   ```bash
   mise exec -- rask ./svc/ctrl/worker/cron/deployanomaly
   ```

3. Run the dashboard contract test.

   ```bash
   mise exec -- pnpm --dir=web exec vitest run \
     internal/clickhouse/src/alert-thresholds-contract.test.ts
   ```

4. Update `web/internal/clickhouse/src/alert-thresholds.ts` if the contract
   reports a difference, then rerun both tests.
5. Review expected alert volume before deploying.

A lower `k` increases alert sensitivity.

Do not change the 5-minute window, minimum baseline buckets, or metric floors as
part of a sensitivity-only change.

## Change the shard count

The default shard count is 16. Change it only when measured shard query latency
or concurrency supports the change.

1. Update the default used by `RunDeployAnomalyCheck`.
2. Keep `<window_start_ms>/<shard>/<shard_count>` as the shard key format.
3. Verify that every shard index from zero through `shard_count - 1` is invoked.
4. Verify that ClickHouse applies
   `cityHash64(workspace_id) % shard_count` with the same count.
5. Verify that the Go filter applies
   `city.CH64(workspace_id) % shardCount == shard` with the same count.
6. Verify that a window calls the previous window with the new shard count. An
   absent predecessor must evaluate under the new partition. Group objects
   reject windows that they already evaluated under the old partition.
7. Measure candidate rows, per-shard query p95, end-to-end cron p95, and peak
   child concurrency.
8. Deploy the code before changing any production cron assumptions.

A count change applies to the new window and any predecessor shard keys that it
evaluates during catch-up. Do not restart an in-flight window with a different
count.

## Verify the production cron

The local chart is not the production source of truth. The production
`deploy-anomaly-check` job is in the `unkeyed/infra` repository at
`eks-cluster/helm-chart/restate/environments/{canary,production001}/us-east-1.yaml`.
Both environments use `*/5 * * * *` and a fresh idempotency key for each window.

The request must calculate the window that closed one full bucket earlier and
invoke this path:

```bash
window_start=$(($(date -u +%s) / 300 * 300 - 600))

curl --fail-with-body \
  -X POST \
  -H 'content-type: application/json' \
  -H "idempotency-key: deploy-anomaly-${window_start}" \
  "${RESTATE_INGRESS_URL}/hydra.v1.CronService/deploy-anomaly-${window_start}/RunDeployAnomalyCheck/send" \
  -d '{}'
```

Configure a 5-minute cadence, forbidden concurrent Kubernetes jobs, bounded
caller retries, and the kill-on-max-attempts Restate policy. After deployment,
confirm one cron invocation, all shard invocations, all child results, and a
success heartbeat for the same window.
