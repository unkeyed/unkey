---
title: "Troubleshoot private networking"
description: "Detect, locate, and fix failures in app bindings across Ctrl, Krane, and undns with Prometheus metrics and logs"
---

Private networking has three stages. Ctrl selects a target deployment for every binding. Krane publishes that selection as Kubernetes objects and Cilium policies. The regional `undns` resolver answers `<alias>.unkey.internal` from those objects. A failure in one stage shows up as a DNS or connection error in the calling app, so start from the symptom and follow it upstream.

```plaintext
Ctrl snapshot ──▶ Krane leader ──▶ ConfigMaps, Services,      ──▶ undns ──▶ caller Pod
(selection)       (publication)    EndpointSlices, policies       (answers)
unkey_control_*   unkey_krane_private_network_*                  unkey_dns_*
```

## Choose where to query

Each deploy cluster runs its own Prometheus (kube-prometheus-stack), which scrapes services through ServiceMonitors and remote-writes to global Thanos. The two stores label series differently:

| Store | Scope | Cluster identity |
| --- | --- | --- |
| Regional Prometheus, `https://prometheus-<region>-<environment>.dojo-blenny.ts.net` | One cluster | None on the series. `cluster`, `environment`, and `region` are external labels, visible only as `$externalLabels` in alert templates |
| Global Thanos | Every cluster | `cluster` (`deploy-<region>`), `environment`, and `region` on every series |

The queries on this page are written for the regional Prometheus. For global Thanos, add `environment, region` to every `by` clause, or filter with `{environment="production001", region="us-east-1"}`.

ServiceMonitors set `job` to the Service name:

| Service | Selector | Source |
| --- | --- | --- |
| Krane | `job="krane", namespace="unkey"` | `infra` Helm chart `krane` |
| Ctrl API | `job="control-api", namespace="control"` | `infra` Helm chart `control-api`, deployed in the control plane regions |
| undns | `job="undns", namespace="unkey"` (assumed) | `infra` has no undns chart or ServiceMonitor yet. The selector follows the Cilium policy that allows `app: undns` in `unkey`. Change it to match the chart when it exists |

Krane exports `unkey_krane_private_network_*` only when `private_network.enabled` is set. No `infra` environment enables it yet. Scope every private networking check to the regions where it's enabled, which the examples show as `region=~"us-east-1|eu-central-1"`.

## Confirm that telemetry arrives

A query that looks for a bad value returns nothing both when the system is healthy and when the metric is gone. Check that telemetry arrives before you trust an empty result.

| State | Krane | undns |
| --- | --- | --- |
| Healthy and idle | `up` is 1. One replica reports `unkey_krane_private_network_leader` 1, the others 0. Entries are 0. The discovery pass age stays below about 35 seconds: the 30 second scrape interval plus the 5 second poll | `up` is 1. `unkey_dns_discovery_ready` is 1. `unkey_dns_queries_total` can be missing because no query arrived since start |
| No telemetry | `up` is 0 or missing, or `unkey_krane_private_network_leader` is missing | `up` is 0 or missing |

```plaintext
# Krane isn't scraped, or every target is down
absent(up{job="krane", namespace="unkey"} == 1)

# Krane is scraped, but exports no private network metrics
absent(unkey_krane_private_network_leader{job="krane", namespace="unkey"})

# No replica leads, including when the metric is missing
absent(unkey_krane_private_network_leader{job="krane", namespace="unkey"} == 1)

# Seconds since each Krane loop last processed its whole input
time() - max by (loop) (
  unkey_krane_private_network_last_completed_pass_unix_seconds{job="krane", namespace="unkey"}
)

# undns isn't scraped, or every target is down
absent(up{job="undns", namespace="unkey"} == 1)
```

`absent()` over a comparison returns a sample without labels, so alert text must take the region from `$externalLabels`. `max(unkey_krane_private_network_leader) == 0` returns nothing when every replica is gone, so don't use it on its own. The leader exports its completion timestamps at 0 when it acquires the Lease, so a leader that never completes a pass shows a large age instead of no series.

In global Thanos, one query finds every expected region where Krane is scraped but no replica leads. It includes regions where Krane is down or exports no private network metrics:

```plaintext
group by (environment, region) (
  up{job="krane", namespace="unkey", environment="production001", region=~"us-east-1|eu-central-1"}
)
unless on (environment, region)
group by (environment, region) (
  unkey_krane_private_network_leader{job="krane", namespace="unkey"} == 1
)
```

A region whose Krane has no `up` series at all needs one `absent(up{job="krane", namespace="unkey", region="<region>"})` per expected region. A region whose Prometheus stops remote-writing is covered by the regional watchdog heartbeat alert.

Every Krane leader asks Ctrl for a snapshot every 5 seconds, even with nothing to publish. Leaders without Ctrl successes point at Ctrl or at telemetry from Ctrl:

```plaintext
count(unkey_krane_private_network_leader{job="krane", namespace="unkey"} == 1)
unless
sum(rate(unkey_control_private_network_snapshots_total{job="control-api", namespace="control", result="success"}[5m])) > 0
```

Run this last query in global Thanos, because Krane and Ctrl run in different clusters. It detects a fleet-wide absence of successful snapshots, not a failure affecting only one leader. Successes elsewhere can hide that failure; use the affected region's Krane `stage="snapshot"` errors to investigate it.

## Detect a problem

With telemetry confirmed, these queries return nothing when the stack is healthy or idle. Each result names the stage to investigate.

```plaintext
# Private DNS answers that failed, by reason
sum by (reason) (
  rate(unkey_dns_queries_total{job="undns", namespace="unkey", path="private", rcode=~"SERVFAIL|REFUSED"}[5m])
) > 0

# Public forwards that undns failed; reason="upstream" is CoreDNS's own answer
sum by (reason) (
  rate(unkey_dns_queries_total{job="undns", namespace="unkey", path="public", rcode="SERVFAIL", reason!="upstream"}[5m])
) > 0

# undns replicas that can't answer private names
unkey_dns_discovery_ready{job="undns", namespace="unkey"} == 0

# Entries whose publication failed; previous objects stay published
max by (kind) (unkey_krane_private_network_entries{job="krane", namespace="unkey", state="failed"}) > 0

# Ctrl snapshot failures, in the control plane regions
sum by (result) (
  rate(unkey_control_private_network_snapshots_total{job="control-api", namespace="control", result!="success"}[5m])
) > 0
```

### Bindings waiting for endpoints

A binding target switch waits until the new target has a ready endpoint, which is normal during a rollout. The gauge counts waiting entries, not which entries wait:

```plaintext
min_over_time(
  max(unkey_krane_private_network_entries{job="krane", namespace="unkey", state="waiting_for_endpoints"})[15m:]
) > 0
```

A result means at least one binding waited at every evaluation in the window. It doesn't mean the same binding waited for 15 minutes: bindings that take turns keep the count above zero. To find which binding waits and for how long, search Krane logs for `private network binding keeps its previous target until the new target has ready endpoints`. The wait for a `binding_key` lasts until the next `private network binding published` log with the same `binding_key`.

## Find what is wrong

Each metric has a label that names the failed step. Read the label, then use the matching table below.

```plaintext
# Serving state of published bindings; each undns replica counts every binding
max by (kind, state) (unkey_dns_bindings{job="undns", namespace="unkey"}) > 0

# Which discovery watch is unhealthy
unkey_dns_discovery_watch_healthy{job="undns", namespace="unkey"} == 0

# Which limit sheds queries
sum by (limit) (rate(unkey_dns_shed_total{job="undns", namespace="unkey"}[5m])) > 0

# Which Krane step fails
sum by (loop, stage) (increase(unkey_krane_private_network_errors_total{job="krane", namespace="unkey"}[15m])) > 0

# undns latency by path; public answers include CoreDNS
histogram_quantile(0.99,
  sum by (path, le) (rate(unkey_dns_query_duration_seconds_bucket{job="undns", namespace="unkey"}[5m])))

# Krane passes near their 30 second deadline
histogram_quantile(0.99,
  sum by (loop, le) (rate(unkey_krane_private_network_pass_duration_seconds_bucket{job="krane", namespace="unkey"}[15m])))

# Ctrl snapshot database read time
histogram_quantile(0.99,
  sum by (le) (rate(unkey_control_private_network_snapshot_read_duration_seconds_bucket{job="control-api", namespace="control"}[15m])))
```

`unkey_dns_bindings` and `unkey_krane_private_network_entries` count different things. Krane counts snapshot entries it tried to publish. `undns` counts binding ConfigMaps it can see and the answer a query would get now. A cluster where Krane reports current entries but `undns` reports no bindings points at `undns` RBAC or label selection. `undns` refreshes binding states every second while all four discovery watches are healthy, and keeps the last values while any watch is unhealthy.

### undns reasons

`unkey_dns_queries_total` has `path` (`private`, `public`, or `invalid`), `reason`, `rcode`, and `transport` labels. `unkey_dns_bindings` uses the same reason names for binding states, plus `active` and `pending_revision`.

| Reason | Response | Cause | Confirm | Fix |
| --- | --- | --- | --- | --- |
| `identity_unavailable` | SERVFAIL | The Pod watch is failed or stale, so no caller is known | `unkey_dns_discovery_watch_healthy{resource="pods"}` is 0; `DNS discovery watch failed` logs with `resource=pods` | Restore API server access or RBAC. `undns` recovers when the watch renews |
| `discovery_not_ready` | SERVFAIL | Another watch is failed or stale, or this replica hasn't finished its first sync and activation | `unkey_dns_discovery_watch_healthy` names the resource; a recently started Pod | Same as above. A new replica clears this after it syncs |
| `unknown_caller` | REFUSED | No Krane deployment Pod in the cache has the source IP | `DNS query failed` sample log `source`; `kubectl get pods -A -o wide --field-selector status.podIP=<ip>` | A node IP as source means source IPs aren't preserved. A non-Krane Pod must use cluster DNS. A new Pod can hit this until the Pod watch delivers it |
| `ambiguous_caller` | REFUSED | Two or more cached Pods that aren't Succeeded or Failed share the source IP | See [ambiguous callers](#ambiguous-callers) | See [ambiguous callers](#ambiguous-callers) |
| `ineligible_caller` | REFUSED | The Pod isn't Running, is terminating, uses host networking, or lacks Krane identity or environment kind labels | Pod labels, phase, and `deletionTimestamp` | Redeploy the calling deployment so Krane labels it |
| `binding_unresolved` | SERVFAIL | Ctrl selected no target for the binding | Krane `unresolved` entries; [the selection checks](#check-why-ctrl-selected-no-target) | Deploy the target, or change the binding target. Normal for previews without a matching branch |
| `binding_ambiguous` | SERVFAIL | Two ConfigMaps publish the same caller and alias | `kubectl get cm -A -l app.kubernetes.io/component=private-dns,unkey.com/caller-deployment.id=<id>` | Escalate. This is a manual copy or a Krane defect |
| `binding_invalid` | SERVFAIL | A binding ConfigMap is malformed or changed without a new revision | `private DNS binding cannot be served` log `error` | Delete the ConfigMap. Krane recreates it within 5 seconds |
| `service_missing` | SERVFAIL | The binding's discovery Service doesn't exist | Krane errors with `stage="service"` | Fix the Krane failure. Don't recreate the Service by hand |
| `service_rejected` | SERVFAIL | The Service doesn't match the binding or isn't headless without unready addresses | `private DNS binding cannot be served` log `error` | Find who edited the Service. Krane refuses to replace foreign objects |
| `service_retired` | SERVFAIL | The binding still points at a Service past its retirement deadline | Krane discovery pass age and `waiting_for_endpoints` entries | Fix the Krane stall or the missing target endpoints |
| `no_ready_endpoints` | SERVFAIL | The serving target has no ready Pods in any region this cluster sees | `kubectl get endpointslices -n <ns> -l kubernetes.io/service-name=<service>`; target Pod readiness; Krane errors with `stage="endpoint_slice"` | Fix the target deployment. For remote regions, check Cilium ClusterMesh status |
| `lookup_error` | SERVFAIL | An informer index failed | `DNS query failed` log `reason` and `error_type` | Escalate. This is a defect |
| `shed` | SERVFAIL | A concurrency limit is full | `unkey_dns_shed_total{limit}`; `DNS query failed` log `workspace_id` | See [shed queries](#shed-queries) |
| `upstream_timeout` | SERVFAIL | CoreDNS didn't answer within `forward_timeout` | Public latency; CoreDNS Pods and their metrics | Fix CoreDNS. Raising `forward_timeout` holds forward slots longer |
| `upstream_error` | SERVFAIL | undns couldn't reach CoreDNS | `DNS query failed` log `error_type`; CoreDNS Service endpoints and health | Check the configured `upstream` IP and CoreDNS Service |
| `upstream_invalid` | SERVFAIL | CoreDNS answered a different question or a malformed message | `DNS query failed` log | Escalate with a packet capture |
| `pack_error` | SERVFAIL | undns couldn't encode its response | `pack DNS response` log | Escalate. This is a defect |

Other outcomes report `answer`, `nodata` (AAAA), `unknown_name` (NXDOMAIN), `unsupported_type`, or `upstream`. NXDOMAIN means the caller has no binding with that alias or queried a multi-label private name. See the <a href="https://www.unkey.com/docs/networking/private-networking/troubleshooting" target="_blank">product troubleshooting page</a> for customer causes.

`pending_revision` in `unkey_dns_bindings` means `undns` still answers with the previous target because the new one has no ready endpoints here. It explains answers that point at an older deployment.

### Ambiguous callers

The Pod index drops Succeeded and Failed Pods, so terminal Pods never cause `ambiguous_caller`. Two Pods that still hold the same IP do. That happens when the CNI already released the IP of a terminating Pod, whose phase is still Running, and assigned it to a new Pod. It also happens when a Pod on a lost node stays in phase Unknown while its IP range moves to another node.

1. Take the source IP from the `DNS query failed` sample log.
2. Run `kubectl get pods -A -o wide --field-selector status.podIP=<ip>` and read each Pod's phase, node, and `deletionTimestamp`.
3. If the API server shows two Pods, the older one is terminating or on a lost node. Let a terminating Pod finish its grace period. Force-delete a Pod only after you confirm with `kubectl get node <node>` that its node is gone.
4. If the API server shows one Pod, this `undns` replica's cache is behind. Check `unkey_dns_discovery_watch_healthy{resource="pods"}` for that replica.

### Shed queries

undns admits every query through one pool, `queries_in_flight`, before it decides whether the name is private or public. The query holds that slot while undns identifies the caller and answers a private name. Then it releases the slot. A public query takes a separate slot from `forwards_in_flight` only for the upstream call. The `limit` label on `unkey_dns_shed_total` separates the causes:

- `queries`: admission is saturated. Queries of every path are rejected, and the `path` label on `unkey_dns_queries_total{reason="shed"}` shows which queries were rejected, not which ones caused the load. Check undns CPU throttling, the total query rate, and `path="private"` latency.
- `forwards`: every forward slot waits on CoreDNS. High `path="public"` latency means CoreDNS is slow, not that the limit is small.
- `forwards_per_workspace`: one workspace fills its share. The sample log names the workspace.
- `forwards_unidentified`: callers without a Pod identity share one small quota. Check the Pod watch first, because a failed or unsynced watch moves every caller into this quota.

Raise a limit only after you rule out CPU starvation and a slow upstream. Scaling `undns` replicas adds capacity without changing per-replica fairness.

### Krane stages

`unkey_krane_private_network_errors_total` has `loop` (`discovery` or `endpoints`) and `stage` labels. `list` and `snapshot` abort the pass. Every other stage fails one entry, and that entry keeps its previously published objects.

| Stage | Cause | Confirm | Fix |
| --- | --- | --- | --- |
| `snapshot` | Ctrl is unreachable, rejects Krane, or the stream ended early | `unkey_control_private_network_snapshots_total` by `result`; `private network reconciliation failed` log | Fix Ctrl or the Krane credentials |
| `list` | Kubernetes reads fail | Log error; Krane RBAC | Restore API server access |
| `invalid_entry` | Ctrl sent an entry Krane can't publish, such as a duplicate identity or an alias that isn't a DNS label | `private network entry failed to publish` log | Fix the binding data |
| `namespace`, `service`, `endpoint_slice`, `binding` | Kubernetes rejected a write, the namespace is terminating, or a foreign object has the name | Log `stage` and `error`, for example `refuse to replace foreign` | Fix RBAC or remove the conflicting object |
| `policy` | Cilium rejected the binding policy or the CRD is missing | Log error; `kubectl get ciliumnetworkpolicies -n <ns> -l unkey.com/binding.id=<id>` | Fix Cilium. Until then the caller keeps its previous grant |
| `cleanup` | Revoking objects missing from the snapshot failed | Log error | Fix promptly: revoked bindings can keep their network grant until cleanup succeeds |

Krane logs a failing entry once when it starts failing or fails at a new stage, and once when it recovers. Search for `private network entry failed to publish` and filter by `binding_id` or `caller_deployment_id`.

If no replica leads, check the Lease:

```bash
kubectl -n kube-system get lease krane-private-network -o yaml
```

The namespace is `private_network.lease_namespace`. A stale `renewTime` with a live holder means that replica can't reach the API server. Krane exits when it loses the Lease.

### Ctrl results

`unkey_control_private_network_snapshots_total` has a `result` label:

- `unauthenticated`: Krane's bearer token doesn't match Ctrl.
- `unknown_cluster`: the Krane cluster key (cell, platform, region) is invalid or has no cluster row. Check the Krane cluster configuration.
- `database_error`: looking up the cluster or reading bindings and replicas failed. Check database health and the read duration.
- `send_error`: Krane disconnected while the snapshot streamed. It often follows long reads, because Krane gives up after 30 seconds.

### Check why Ctrl selected no target

Metrics can't say why one binding is unresolved, because the answer depends on database state. The selection rules are the `binding_candidates` query in `svc/ctrl/internal/db/queries/private_network_list_bindings.sql`. Take `binding_id` and `caller_deployment_id` from a Krane or `undns` log, then check each rule in order.

A binding appears in the snapshot only while its caller deployment is `deploying` or `ready`, has `desired_state = 'running'`, and has a running topology on the cluster's platform. A caller that fails this has no entry, so its queries get NXDOMAIN, not SERVFAIL.

Read the binding rule and the caller context:

```sql
SELECT b.selection_mode, b.resource_id AS target_app_id,
       b.target_deployment_id, b.target_environment_id,
       target_app.current_deployment_id,
       caller_env.kind AS caller_environment_kind,
       caller.source AS caller_source, caller.git_branch AS caller_branch,
       caller.fork_repository_full_name AS caller_fork
FROM app_bindings b
JOIN apps target_app ON target_app.id = b.resource_id
JOIN deployments caller ON caller.id = '<caller_deployment_id>'
  AND caller.app_id = b.app_id
JOIN environments caller_env ON caller_env.id = caller.environment_id
WHERE b.id = '<binding_id>';
```

The rule decides which deployment Ctrl selects:

| `selection_mode` | Caller | Selected deployment |
| --- | --- | --- |
| `deployment` | Any | `target_deployment_id` |
| `automatic` | Production environment | The target app's live deployment, `current_deployment_id` |
| `automatic` | Preview environment, `source = 'git'`, non-empty branch | The newest target deployment in a preview environment with the same branch and fork that was ever ready (`first_ready_at` set) |
| `automatic` | Preview environment without a Git branch | None |
| `environment` | Any | The target app's live deployment if it belongs to `target_environment_id`. Otherwise, if that environment is a preview environment, its newest deployment that was ever ready. Otherwise none |

For an automatic preview binding, list the candidates. Use an empty string when `caller_fork` is NULL:

```sql
SELECT d.id, d.status, d.desired_state, d.first_ready_at, d.created_at
FROM deployments d
JOIN environments e ON e.id = d.environment_id AND e.app_id = d.app_id
WHERE d.app_id = '<target_app_id>' AND e.kind = 'preview'
  AND d.source = 'git' AND d.git_branch = '<caller_branch>'
  AND COALESCE(d.fork_repository_full_name, '') = '<caller fork or empty string>'
ORDER BY d.created_at DESC, d.id DESC
LIMIT 5;
```

For an environment binding, list the deployments of the target environment:

```sql
SELECT d.id, e.kind, d.status, d.desired_state, d.first_ready_at, d.created_at
FROM deployments d
JOIN environments e ON e.id = d.environment_id AND e.app_id = d.app_id
WHERE d.app_id = '<target_app_id>'
  AND d.environment_id = '<target_environment_id>'
ORDER BY d.created_at DESC, d.id DESC
LIMIT 5;
```

The selected candidate is the first row with `first_ready_at` set, even if it's stopped now. Ctrl doesn't fall back to an older running deployment. The selected deployment resolves only if it can run on this cluster's platform:

```sql
SELECT d.status, d.desired_state, dt.desired_status, r.name AS region, r.platform
FROM deployments d
LEFT JOIN deployment_topology dt ON dt.deployment_id = d.id
LEFT JOIN regions r ON r.id = dt.region_id
WHERE d.id = '<selected_deployment_id>';
```

It needs `status = 'ready'`, `desired_state = 'running'`, and a row with `desired_status = 'running'` in a region whose `platform` matches the cluster. When any check fails, Ctrl publishes the binding without a target and `undns` answers SERVFAIL.

## Get the details

Metrics use bounded labels, so they never name a binding, deployment, workspace, or queried DNS name. Query failure logs omit DNS names and raw error messages, which can contain customer queries. They retain the failure reason, error type, and caller identifiers. Binding state logs describe configured bindings, not individual queries. These logs carry the IDs:

| Log message | Service | When |
| --- | --- | --- |
| `private DNS binding cannot be served` | undns | A binding starts failing or changes failure reason |
| `private DNS binding serves its target` | undns | A failing binding recovers |
| `private DNS binding serves its previous target until the new target has ready endpoints` | undns | A new revision waits for endpoints |
| `DNS query failed` | undns | At most one sample per reason per minute |
| `DNS discovery watch failed` | undns | A watch reports an error |
| `private network binding published` | Krane | A binding revision is written, with the previous and new deployment |
| `private network entry failed to publish; its previous objects stay published` | Krane | An entry starts failing or fails at a new stage |
| `private network binding keeps its previous target until the new target has ready endpoints` | Krane | A target switch starts waiting |
| `private network entry recovered` | Krane | A failing entry publishes again |
| `private network leadership acquired` / `lost` | Krane | The Lease changes hands |
| `deployment stop deferred because an app binding pins it` | Ctrl worker | A stop waits because a binding pins the deployment |

## Recover safely

Restarts fix a stuck process. They don't fix API server, RBAC, Ctrl, or CoreDNS failures, so confirm the cause first.

### Restart undns one replica at a time

undns readiness checks only its DNS listeners, so public DNS keeps working when the API server is unavailable. A new replica becomes ready and receives traffic before its discovery watches sync and activation runs. Until then, private queries that reach it get SERVFAIL (`identity_unavailable` or `discovery_not_ready`). Public queries still work, but every caller shares the small `forwards_unidentified` quota until the Pod watch syncs, so a busy replica can shed public queries too. Callers see these failures as transient: their resolver retries can reach another replica, but that's not guaranteed.

1. Delete one Pod.
2. Wait until the replacement reports `unkey_dns_discovery_ready{pod="<new-pod>"} == 1` and every `unkey_dns_discovery_watch_healthy` series for it is 1.
3. Confirm that `path="private"` SERVFAIL for the new Pod returns to its previous rate.
4. Repeat for the next Pod.

Don't restart every replica at once. Private resolution fails for every caller until the new replicas sync. A plain rollout restart can also move faster than discovery, because readiness doesn't wait for it.

### Restart the Krane leader

Published objects stay in place, and `undns` keeps answering from them. The Lease isn't released on shutdown, so another replica takes over within about 17 seconds of the last renewal (the 15 second lease plus one 2 second retry) and then runs its first pass. In that window, bindings don't follow new deployments, and source EndpointSlices aren't refreshed, so answers can include Pods that stopped. Restart only the current holder, and confirm that `unkey_krane_private_network_leader` is 1 on another replica and that the discovery pass age is back to normal.

### Other steps

- Don't delete or edit discovery Services, EndpointSlices, or binding ConfigMaps by hand, except a malformed ConfigMap. A deleted Service fails its bindings until Krane recreates it.
- Don't raise `undns` limits to hide a slow upstream. Forward slots stay busy for the whole `forward_timeout`.

## What metrics can't tell you

Some failures look healthy in every metric on this page:

- A resolved name with a failing connection. DNS is fine, but a Cilium policy or the target app drops traffic. Use `hubble observe --verdict DROPPED` for the caller Pod, and check that the binding policy exists.
- A caller Pod that doesn't use `undns`. Deployments created before their workspace enrolled, or in a region without `private_network.resolver_ip`, use cluster DNS. `undns` sees no queries from them. Check `dnsConfig.nameservers` in the Pod spec.
- Stale client caches. Clients can cache answers longer than the TTL and keep old connections open after a switch.
- Remote Pod health. Endpoint readiness comes from Kubernetes and Cilium EndpointSlices, not from a probe of the remote Pod.
- Which binding waits or fails, and for how long. The gauges count entries. Use the logs for IDs and durations.
- Every affected query during a flood. The `DNS query failed` log is sampled. The binding state logs are complete.
