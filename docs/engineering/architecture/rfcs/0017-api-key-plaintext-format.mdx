## Summary

This RFC proposes one plaintext format for all Unkey-generated API keys,
including customer API keys and Unkey root keys. The format uses a controlled
prefix, 256 random bits, Bitcoin Base58, a version marker, and a 32-bit CRC-32C
checksum.

Imported and existing keys retain their original plaintext. Verification stays
format-agnostic and uses the SHA-256 hash of the complete value.

## Detailed design

### Format

The general grammar is:

```plaintext
{prefix}_{display_nonce}unkeyv{version}{version_payload}
```

```diagram
┌────────┬───┬────────────────┬────────┬──────────────────────────┐
│ prefix │ _ │ display nonce  │ unkeyv │ version-specific payload │
│ 1–7    │   │ 8 Base58 chars │        │                          │
└────────┴───┴────────────────┴────────┴──────────────────────────┘
```

Version numbering starts at `1`. The version occupies one Base58 character and
increments in Base58 alphabet order. It appears before every version-dependent
field, so a parser can select the payload definition before reading its lengths.

### Prefix

Prefixes must match:

```plaintext
^[A-Za-z0-9_]{0,6}[A-Za-z0-9]$
```

They contain one through seven ASCII letters, numbers, or underscores, and must
end in an alphanumeric character. `prod_sk`, `pk_live`, and `unkey` are valid.
`prod_sk_` and eight-character prefixes are invalid.

### Version 1

Version 1 has this exact shape:

```plaintext
{prefix}_{8 random chars}unkeyv1{36 random chars}{6 checksum chars}
```

| Field | Length | Contents |
| --- | ---: | --- |
| Prefix | 1–7 | Controlled prefix |
| Separator | 1 | `_` |
| Random head | 8 | First part of the random value |
| Marker and version | 7 | Literal `unkeyv1` |
| Random tail | 36 | Rest of the random value |
| Checksum | 6 | Fixed-width Base58 CRC-32C |

The complete key is between 59 and 65 characters.

The random field is the fixed-width, 44-character Bitcoin Base58 encoding of 32
random bytes. It provides 256 random bits. Prefixes, markers, and checksums add
no entropy.

<a href="https://pages.nist.gov/800-63-4/sp800-63b.html" target="_blank">
  NIST SP 800-63B
</a>

#### Checksum

Calculate CRC-32C over the complete key up to, but excluding, the checksum:

```plaintext
unsigned_key   = prefix + "_" + random_head + "unkeyv1" + random_tail
checksum_value = CRC-32C(ASCII(unsigned_key))
checksum_text  = base58Fixed(checksum_value, 6)
key            = unsigned_key + checksum_text
```

The checksum detects corruption and filters unrelated scanner matches with an
approximately 1 in 2³² pass rate. It does not provide entropy or authenticity.

### Parsing and future versions

After the prefix separator, the version 1 body has these fixed offsets:

```diagram
┌──────────┬─────────┬─────────┬─────────────┬──────────┐
│ 0–7      │ 8–13    │ 14      │ 15–50       │ 51–56    │
│ random   │ unkeyv  │ version │ random tail │ checksum │
│ 8 chars  │ 6 chars │ 1 char  │ 36 chars    │ 6 chars  │
└──────────┴─────────┴─────────┴─────────────┴──────────┘
```

A parser reads the prefix separator, eight display characters, `unkeyv`, and
the one-character version before dispatching the remaining value to that
version's parser.

All version-dependent fields follow the version. Version 2 can therefore use a
different random or checksum length without changing version discovery:

```plaintext
{prefix}_{8 random}unkeyv2{version 2 payload}
```

A valid checksum confirms only structural validity. Database state determines
whether a key was issued, is enabled, and remains active.

### GitHub secret scanning

The version 1 secret format is:

```plaintext
[A-Za-z0-9_]{0,6}[A-Za-z0-9]_[1-9A-HJ-NP-Za-km-z]{8}unkeyv1[1-9A-HJ-NP-Za-km-z]{42}
```

Use separate boundaries:

```plaintext
Before: \A|[^A-Za-z0-9_]
After:  \z|[^1-9A-HJ-NP-Za-km-z]
```

GitHub recommends a unique identifier, high-entropy randomness, and a 32-bit
checksum for partner patterns. The scanner or webhook validates CRC-32C before
hashing the complete match and querying the live-key database.

<a href="https://docs.github.com/code-security/secret-scanning/secret-scanning-partnership-program/secret-scanning-partner-program#identify-your-secrets-and-create-regular-expressions" target="_blank">
  GitHub secret scanning partner guidance
</a>

Legacy root keys keep their existing GitHub pattern. Version 1 uses the pattern
above for both root and customer API keys.

### Database representation

Store the format, prefix, first four random characters, and final four
characters for newly generated keys:

```plaintext
format = "unkey_v1"
prefix = "prod_sk"
start  = "K7pQ"
end    = "X2Ks"
```

Display them as `prod_sk_K7pQ...X2Ks`. These fields are display hints, not
identifiers or verification inputs. The final four version 1 characters are
part of the checksum and still vary with the complete key.

Existing non-recoverable keys cannot backfill `end`. Legacy rows retain their
existing `start`, use the `legacy` format, and use `""` for unavailable fields.

### Deprecating configurable lengths

Migration removes request `byteLength`, keyspace `default_bytes`, and dashboard
byte controls without changing existing plaintexts.

1. Mark `byteLength` deprecated, remove dashboard controls, and measure explicit
   lengths, non-default stored lengths, and incompatible prefixes.
2. Make version 1 the default when `byteLength` is omitted. Stop applying
   `default_bytes`. Keep explicit API v2 lengths on observable legacy generation
   until the API v2 sunset. Never silently ignore an explicit length.
3. Remove `byteLength` in the next breaking API version. Remove the legacy
   generator and default-byte readers and writers after API v2 sunsets. Drop the
   unused database column after the rollback window.

## Drawbacks

- New keys are longer, and customers have less control over their shape.
- Migration requires supporting legacy and versioned plaintext generations at
  the same time.
- Every future version requires corresponding parser and secret-scanner support.

## Alternatives

- **Put `unkeyv1` at the beginning:** easier to scan, but customer keys become
  harder to distinguish visually and appear Unkey-branded.
- **Put the version at the end:** keeps the body visually clean, but a parser
  cannot know version-dependent payload and checksum lengths before reaching it.
- **Encode or hide the marker:** produces a more uniform Base58 value, but loses
  the obvious, stable identifier used by secret scanning.
- **Omit the checksum:** shortens keys, but removes a 32-bit filter for secret
  scanning false positives and accidental corruption.
- **Keep caller-selected random lengths:** preserves flexibility, but prevents a
  predictable schema and consistent security strength.
