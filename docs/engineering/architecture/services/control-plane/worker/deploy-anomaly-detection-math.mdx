title: "Deploy anomaly detection math"
description: "Threshold, baseline, confirmation, and recovery rules for Deploy anomalies"

The Deploy anomaly detector combines historical sigma thresholds, error ratios,
a robust request-drop rule, and fixed health thresholds. Every rule evaluates
one closed 5-minute window for one app and production environment.

## Build the trailing baseline

Sigma metrics use up to 288 buckets from the preceding 24 hours. The current
bucket is excluded. ClickHouse returns moments for non-empty buckets. MySQL
supplies the app's `created_at` timestamp through `app_created_at` in the
evaluator request.

`BaselineWindowBuckets` limits zero-padding to the app's lifetime inside the
lookback. First, `AppLifetimeStart` aligns creation down to a 5-minute boundary
and caps it at the start of the 24-hour lookback:

`lifetime_start = max(window_start - 24 hours, floor(app_created_at / 5 minutes) * 5 minutes)`

The available lifetime bucket count is:

`(window_start - lifetime_start) / 5 minutes`

For count-like spike metrics, the detector reconstructs the population mean and
standard deviation after adding zero-valued missing buckets inside that
lifetime. It does not add zeros for time before the app existed. Error metrics
use request-weighted ratios instead of padding ratio buckets.

For example, an app created 30 minutes before the current window has six
possible baseline buckets, not 288. Even if all six contain steady traffic, the
app has fewer than the minimum 12 observed buckets and cannot fire. After at
least 1 hour and 12 observed buckets, the normal rules apply. This prevents a
brand-new app's first stable traffic from looking like a spike against 23 hours
of invented zeros.

The detector migration replays the latest 7 days of closed buckets before it
creates each materialized view. Existing apps therefore have a full 24-hour
baseline and enough request history for the drop rule on the first detector
run. At most, the in-progress bucket during migration can be absent. The
minimums still apply to young apps: spike metrics need 12 observed buckets, or
1 hour, and request drops need 72 observed buckets, or 6 hours.

The longer request-drop ramp-up avoids treating short test runs followed by
silence as an outage.

The dashboard uses the same creation-time padding. Eligibility always counts
observed 5-minute buckets, even when the chart displays hourly points. An hourly
display still needs 12 observed 5-minute buckets for spike bands and 72 for the
request-drop band.

## Apply spike thresholds

`svc/ctrl/worker/cron/deployanomaly/thresholds.json` is the canonical source for
production sigma, deviation-floor, history, and request-drop values. Go embeds
the file for `DefaultConfig`. A dashboard contract test verifies its mirrored
chart constants against the same values.

Request, egress, and CPU spikes use an effective population standard deviation:

`sigma_effective = max(stddev, 0.1 * mean, metric_floor)`

The opening threshold is:

`mean + k * sigma_effective`

The comparison is strict. A current value equal to the threshold does not fire.
Sensitivity selects `k`: low is 5, normal is 4, and high is 3. Unknown or empty
sensitivity uses normal.

| Metric | Absolute deviation floor | Normal-sensitivity example |
| --- | ---: | --- |
| `requests` | 20 requests | Mean 100 and standard deviation 8 produce an effective deviation of 20 and a threshold of 180. A current value of 201 fires. |
| `egress_bytes` | 1,048,576 bytes | Mean 1,000,000 bytes and standard deviation 20,000 bytes produce an effective deviation of 1,048,576 and a threshold of 5,194,304. A current value of 104,857,600 fires. |
| `cpu_seconds` | 1 second | Mean 10 seconds and standard deviation 0.25 seconds produce an effective deviation of 1 and a threshold of 14. A current value of 60 fires. |

The 10% guard keeps a low-variance baseline from making tiny changes appear
extreme. The absolute floor handles a zero or near-zero mean. The current value
must also reach the separate activity floor: 200 requests, 100 MiB of egress,
or 60 CPU seconds. A value can cross the statistical threshold and remain quiet
when its absolute activity is too small. Equality with the statistical
threshold still does not fire.

### Aggregate resource counters

The resource rollup retains each container's minimum and maximum counter values
for the complete 5-minute bucket. The detector calculates:

`container_cpu_seconds = greatest(0, cpu_usage_usec_max - cpu_usage_usec_min) / 1,000,000`

`container_egress_bytes = greatest(0, network_egress_public_bytes_max - network_egress_public_bytes_min)`

It sums every container delta to get the app value for that bucket. The
dashboard uses the same 5-minute deltas. An hourly chart point is the sum of its
5-minute app values, not a new difference across an hour.

Keeping counter bounds across the whole 5-minute bucket is required. Computing
the difference inside an insert block with one 5-second sample makes the
minimum equal the maximum and incorrectly produces a zero delta.

## Compare error ratios

`error_5xx` and `error_4xx` compare the error ratio, not the raw error count:

`current_ratio = current_errors / current_requests`

The baseline mean is request-weighted:

`baseline_ratio = sum(baseline_errors) / sum(baseline_requests)`

The standard deviation is calculated from each non-empty bucket's error ratio.
Its effective value is:

`max(ratio_stddev, 0.1 * baseline_ratio, 0.01)`

An error window crosses the detector only when both conditions are true:

1. `current_ratio > baseline_ratio + k * sigma_effective`.
2. `current_errors - baseline_ratio * current_requests >= 20`.

Using a ratio separates error rate from traffic volume. A raw count of 100
errors means something different in 200 requests than in 1,000,000 requests.
Weighting the baseline mean by requests prevents a low-volume bucket from
having the same influence as a high-volume bucket. The excess-failure floor
then rejects a large percentage change that affects too few requests to be
actionable.

### Work a moderate 5xx example

Suppose the baseline has 100 errors in 10,000 requests. Its weighted ratio is
1%. The per-bucket ratio standard deviation is 0.5%. The 1% absolute floor
makes the effective deviation 1%, so normal sensitivity sets the crossing
threshold at a ratio above 5%.

The current window has 80 errors in 1,000 requests. Its ratio is 8%, expected
failures are 10, and excess failures are 70. It crosses both conditions. The
first window becomes a candidate. A consecutive crossing in the next complete
window opens the alert.

The same numbers for `error_4xx` follow the same two-window rule and store
`0.08` as `observed_value`. Structured detector logs contain the raw error and
request counts, but `alert_events` does not persist them.

### Work a catastrophic 5xx example

A 5xx window is catastrophic when its ratio is at least 50% and it contains at
least 50 failures. For example, 60 failures in 100 requests is a 60% ratio and
opens after one window. The catastrophic shortcut applies only to `error_5xx`.

## Detect sustained request drops

`requests_drop` does not use the lower side of a sigma distribution. It compares
the current value with the median of the preceding 12 complete buckets:

`current < 0.25 * recent_median`

All of these conditions must hold:

- At least 72 baseline buckets have been observed.
- At least nine of the previous 12 buckets contain 200 or more requests.
- The absolute loss, `recent_median - current`, is at least 200 requests.
- Two consecutive complete windows cross the rule.
- A live deployment exists.
- Its `deployments.desired_state` is not `stopped`.
- At least one topology region has `desired_status = 'running'`.

For example, assume the recent median is 1,000 requests, and 10 of the 12
buckets have at least 200 requests. The threshold is 250. A current window with
100 requests loses 900 requests and becomes a candidate. If the next complete
window also has fewer than 250 requests, the detector opens an alert.

The median resists one recent spike or dip. The activity count rejects scheduled
and bursty workloads that are normally idle. A lower sigma threshold cannot
provide those guarantees. A variable baseline can have a negative statistical
lower bound, and a zero request bucket can also mean ingest delay. The explicit
rule models a sustained loss from a recent, active level instead.

The dashboard draws the request-drop boundary only after the same eligibility
checks pass: 72 observed 5-minute buckets, at least 9 of the preceding 12
buckets with 200 or more requests, and at least 200 requests of absolute loss.

The alert stores the recent median in `baseline_mean` and stores zero in
`baseline_stddev` and `threshold_sigma`. The detector metadata records the last
condition as `deployment_has_running_region`.

No live deployment, `deployments.desired_state = 'stopped'`, or every topology
region being stopped suppresses the rule. Any of those conditions resolves an
open drop alert with `Deployment stopped`.

`autoscaling_replicas_min = 0` does not suppress the rule. A deployment that can
scale to zero still has an unexpected request drop when its deployment and at
least one topology region remain active.

## Apply fixed thresholds

Memory and instance health events do not need a historical baseline. Their
stored `baseline_mean`, `baseline_stddev`, and `threshold_sigma` values are zero.

For memory, each container's 5-minute utilization is its raw utilization sum
divided by its valid sample count. The detector averages containers into an
instance, then averages instances with equal weight to get the app value. The
dashboard uses the same order at both 5-minute and hourly display resolutions.

| Metric | Opening rule | Example |
| --- | --- | --- |
| `memory_utilization` | 5-minute average across instances is at least 90%. | An average of 0.91 opens after one window. An average of 0.90 also opens. |
| `oom_killed` | At least one `OOMKilled` terminated event. | One event opens after one window. |
| `crash_loop` | At least one `CrashLoopBackOff` waiting event. | Two events open one alert after one window. |

Memory requires a complete resources window. An OOM or crash-loop event row is
actionable even when the resources watermark is incomplete. When there is no
event row, resources completeness determines whether the event count is a
complete zero or incomplete. The instance-event ingest buffer is lossy, so a
dropped event can cause a missed alert, but it cannot leave detection stuck on
an incomplete event source.

## Confirm sustained conditions

Moderate error spikes and request drops need two consecutive anomalous windows.
The virtual object stores the candidate window start and verifies that the next
start is exactly 5 minutes later. A normal, insufficient, or non-consecutive
window clears the candidate.

Request spikes, egress spikes, CPU spikes, memory pressure, OOM kills, crash
loops, and catastrophic 5xx errors open after one complete window.

The virtual object also stores `last_window_end`. An evaluation with a window
end equal to or older than that value is a strict no-op. A delayed retry cannot
recreate an old candidate or change recovery state after a newer window.

## Recover against the opening snapshot

When an alert opens, the detector snapshots its baseline mean, effective
standard deviation, sigma multiplier, and opening threshold. It does not use a
later rolling baseline for recovery. A sustained incident would otherwise enter
the baseline and redefine the bad behavior as normal.

Sigma and error metrics use a one-sigma hysteresis band:

`recovery_threshold = opening_mean + (k - 1) * opening_sigma_effective`

For the request-spike example, the opening threshold is 180. Recovery uses
`100 + (4 - 1) * 20 = 160`. Values at or below 160 count as recovered. Values
above 160 reset the quiet count and update the open alert.

Other metrics use rule-specific recovery against the opening snapshot:

| Metric | Recovered window |
| --- | --- |
| `requests_drop` | Requests return to at least the snapshotted 25% median threshold. |
| `memory_utilization` | Utilization falls below 85%. |
| `oom_killed` | The complete window has zero events. |
| `crash_loop` | The complete window has zero events. |

Three consecutive complete recovered windows resolve the alert with the message
`Metric returned to baseline for 3 consecutive windows`. Any anomalous window
before the third resets the count. An incomplete window neither increments nor
resets it.

Recovery also has a maximum open duration. `DefaultConfig` sets
`Config.MaxOpenDuration` to 24 hours. At the first complete evaluation at or
after that age, the detector resolves the alert with
`Baseline adapted after 24 hours`, even if the current value has not crossed the
snapshot recovery threshold.

This limit handles a permanent level shift. After 24 hours, the entire rolling
baseline reflects the new behavior, so the opening snapshot no longer describes
the current operating level. The age-based resolution closes that incident and
lets later departures from the adapted baseline create a new alert. An
incomplete window remains a strict no-op, so it cannot perform the age-based
resolution.

App and environment deletion are lifecycle resolutions, not detector recovery.
Their deletion workflows durably resolve open alerts with `Deployment stopped`
before removing metadata. Shard reconciliation applies the same resolution to
an orphaned open group when the app or environment is already missing.
