## Detection model

Deploy anomaly detection evaluates closed 5-minute windows. The baseline contains up to 288 buckets from the preceding 24 hours and excludes the current bucket.

For request, egress, and CPU spikes, the detector fires when:

`current > mean + k * max(stddev, mean * 0.1, metric floor)`

Normal sensitivity uses `k = 4`. Low sensitivity uses `k = 5`. High sensitivity uses `k = 3`. At least 12 observed baseline buckets are required.

Missing count buckets are zero. Padding starts at the app's first observed bucket, not at the start of the 24-hour lookback. This prevents a new app with steady traffic from treating time before its creation as zero and firing a false ramp-up alert.

## Error rates

The 4xx and 5xx signals evaluate `errors / requests`, not raw error counts. The baseline mean is `sum(errors) / sum(requests)`. Its standard deviation is the population standard deviation of each bucket's ratio. The effective standard deviation floor is 0.01.

An error-rate crossing must cause at least 20 more failures than the baseline rate predicts. This permits a window with 99 failures from 99 requests to alert, while traffic growth at an unchanged error rate does not alert.

Moderate error-rate anomalies need two consecutive complete windows. A 5xx ratio of at least 50% with at least 50 failures is catastrophic and opens after one complete window. The system also persists 4xx alerts.

## Request drops

Request drops use a robust recent level instead of a lower z-score. The recent level is the median of the preceding 12 complete buckets. A drop is anomalous when all of these conditions are true:

- Current requests are below 25% of the recent level.
- At least 9 of the 12 recent buckets have at least 200 requests.
- The absolute loss is at least 200 requests.
- At least 72 observed baseline buckets, or 6 hours, exist.

The activity test applies to the baseline. Zero current traffic can be an outage, but zero traffic after quiet baseline traffic is normal. Alternating burst and idle traffic does not meet the 9-of-12 test.

Request drops need two consecutive complete windows. One empty bucket can be ingest lag through Frontline's buffer and the per-minute and per-5-minute materialized views.

The per-app evaluator suppresses request-drop alerts when no live deployment exists or its desired state is `stopped`. The caller must also suppress intentionally paused or scaled-to-zero deployments when those states are available.

## Resource and instance thresholds

| Metric | Standard deviation floor | Minimum activity |
| --- | ---: | ---: |
| Requests | 20 requests | 200 requests |
| Egress | 1 MiB | 100 MiB |
| CPU | 1 second | 60 seconds |

Memory opens at 90% and recovers below 85%. The current value is the 5-minute average across instances. A secondary maximum remains available for diagnosis. The average avoids one short sample from opening an alert for the whole app.

OOM kills and crash loops open when the count reaches one. They are catastrophic and open after one complete window because the first occurrence is actionable.

## Grouping

The group key is `(workspace_id, project_id, app_id, environment_id)`. Deployment ID is context. App and environment remain stable across a rollout, so an incident stays open when the deployment changes.

Only production environments are evaluated.

## Telemetry completeness

Before fan-out, the orchestrator reads fleet-wide watermarks for the request and resource rollups. A source is incomplete when its exclusive watermark is earlier than the evaluated window end.

Each metric input has one of three states:

- `present`: the source and group have a current bucket.
- `zero_complete`: the source is complete but the group has no current bucket.
- `incomplete`: the source has not completed the window.

An incomplete metric is a strict no-op. It cannot create or confirm a candidate, open or touch an alert, advance recovery, or resolve an alert. Structured logs expose these skips for pipeline monitoring. Only `zero_complete` can be interpreted as zero.

For an active request-drop candidate or alert, `zero_complete` means traffic is still zero and the evaluator reuses the stored opening inputs. For spike metrics it is a recovered value.

## Orchestration and state

The cron runs every 5 minutes. Its virtual object key is `deploy-anomaly-<window_start_unix_seconds>`. The local schedule computes the previous aligned window with:

```bash
$(( ($(date -u +%s) / 300) * 300 - 300 ))
```

The window handler fans out to 16 shard virtual objects by default. A shard key is `<window_start_ms>/<shard>/<shard_count>`, and workspace assignment is `cityHash64(workspace_id) % shard_count`. The window handler receives only counts from each shard, so it never journals fleet metric rows.

Each shard runs ClickHouse candidate queries and adds explicit keys for open alerts and candidates from the preceding window. SQL uses the production thresholds but may over-include. The Go detector remains authoritative. Metadata is resolved in MySQL batches of at most 500 groups. Non-production groups are dropped, and the remaining groups are sorted before fan-out to keep Restate journal positions stable. A child failure fails its shard, prevents the window heartbeat, and allows the next scheduled window to retry.

Request counts use the shard-ordered `frontline_requests_anomaly_per_5m_v1` rollup. Egress and CPU use `instance_resources_app_per_5m_v1`. Memory uses `instance_memory_container_per_5m_v1`, which preserves container and instance grain while reducing the source from one-minute to five-minute rows. These rollups inherit the source tables' dashboards-only caveat and can double-count retried inserts, so they must not be used for billing.

The rollups have no historical migration backfill. New installations need 12 complete buckets before spike detection and 72 complete buckets before request-drop detection.

The per-group virtual object key is `<workspace_id>/<app_id>/<environment_id>`. It owns these keys for each metric:

- `candidate:<metric>` and `candidate_window:<metric>`
- `open_alert:<metric>`
- `fired_at:<metric>`
- `quiet:<metric>`
- `snapshot:<metric>`
- `detector_input:<metric>`

The candidate window makes confirmation consecutive even though each cron window has a different orchestrator key. Open alerts are reconciled from MySQL when a group evaluator first runs.

## Resolution

An open alert keeps the baseline and effective deviation snapshot used when it opened. Recovery compares complete windows with this snapshot, not the rolling baseline, because a sustained incident can raise the rolling baseline.

Sigma metrics recover below `mean + (k - 1) * effective_stddev`. Error ratios use the same recovery band. Request drops recover at the 25% opening threshold. Three consecutive recovered complete windows resolve the alert with:

`Metric returned to baseline for 3 consecutive windows`

A stopped deployment resolves a request-drop alert with `Deployment stopped`.

A permanent level shift can remain outside the opening snapshot's recovery band. The evaluator therefore resolves an alert on the first complete window whose end is at least 24 hours after `fired_at`, when the rolling baseline has fully adapted. The resolution message is `Baseline adapted after 24 hours`.

Detector inputs are written as structured log fields when an alert opens. The current `alert_events` schema has no context JSON column, so raw error and request counts are not persisted.

## Notifications

This phase does not send notifications. It persists opening, `last_seen_at`, `status`, and `resolved_at` transitions in `alert_events`. A future notification service will consume those transitions. It will need the alert ID, workspace slug, app and environment, metric, observed and baseline values, and `fired_at`. Workspace, app, and environment names can be resolved from their persisted IDs.

## Scale characteristics

Restate's <a href="https://docs.restate.dev/server/networking" target="_blank">`networking.message-size-limit`</a> defaults to exactly 32 MiB. The invoker limit defaults to the same global setting and is clamped to it. Restate rejects an oversized `ctx.Run` result or journal request with `RT0003`. The Go SDK uses its JSON codec for these results.

The original unsharded request query returned every active group. At 100,000 groups its JSON result was 57,952,008 bytes, already above the default Restate limit. Linear extrapolation gives about 580 MB at one million groups.

The scale test inserts 288 request buckets with three status codes and 1,440 resource rows for each group. It makes 0.5% of current windows anomalous. Post-change query duration is the sum of 16 shard queries run sequentially by the harness. Production starts the shard calls concurrently, so this sum is not production wall time. Peak memory is the largest query, not a sum.

The old resource query failed because its aggregation tried to spill about 15 GB with only 14 GB of temporary disk available. The app and container five-minute rollups keep the post-change peak below 1 GB in this test.

The orb had 31 GiB RAM and 16 GiB free disk. One million groups, which require more than 2.3 billion generated source rows, did not fit. Linear extrapolation from 100,000 groups gives about 5,000 rows at the Go layer. It gives 2.91 MB total request JSON and 2.51 MB total resource JSON, with about 244 KB and 210 KB in the largest shard journal entries. These are estimates, not measured results.

Candidate filtering, explicit open and pending group filters, and the rollups bound data returned to Go. A naive 16-shard hash predicate without shard-ordered storage scanned the request fleet 16 times: 1.387 billion rows and 24,458 ms at 100,000 groups. Shard-ordered rollups reduced that intermediate result to 36.38 million rows and 4,311 ms.

Watermarks come from the two-row `anomaly_source_watermarks_v1` rollup, and the read is bounded to two hours. The watermark remains fleet-wide. A healthy region can therefore hide a lagging region, and that region's absent rows can appear as complete zero traffic. Per-region watermarks require region identity in all source rows and are deferred to phase 2.

## Code

The pure detector and Restate handlers live in `svc/ctrl/worker/cron/deployanomaly`. Fleet queries live in `pkg/clickhouse/anomaly_window.go`.

Run the focused checks with:

```bash
mise exec -- rask ./svc/ctrl/worker/cron/deployanomaly/...
mise exec -- rask ./pkg/clickhouse/...

UNKEY_ANOMALY_SCALE_GROUPS=10000 mise exec -- go test -run '^TestAnomalyWindowsScale$' -count=1 -v ./pkg/clickhouse
```
