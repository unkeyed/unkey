---
title: "WorkOS roles"
description: "How WorkOS roles map to Unkey resource permissions"
---

WorkOS is authoritative for a user's assigned organization roles. We define the
permissions for each role in the API.

The WorkOS session cookie contains a sealed access token. Assigning every Unkey
permission to a WorkOS role adds every permission slug to that token. The token
can then exceed the browser's cookie size limit. We avoid this limit by
transporting role claims instead of permission claims. The API expands the
roles into permissions.

## Role claims

WorkOS access tokens contain the built-in `roles` claim. It contains all
organization membership roles assigned to the user.

The API does not read the singular `role` claim. An absent or empty `roles`
claim maps to no permissions.

Set `provider = "workos"` on the JWT authentication entry to enable role
mapping. The API does not infer the provider from the issuer.

## Configure WorkOS roles

Create the roles manually in each WorkOS environment. Open the
<a
  href="https://dashboard.workos.com/environment/authorization/"
  target="_blank"
>
  Authorization page
</a>
in the WorkOS Dashboard.

1. Select the WorkOS environment.
2. Click **Create role**.
3. Create **Developer** with the immutable slug `developer`.
4. Create **Viewer** with the immutable slug `viewer`.
5. Leave both roles without WorkOS permissions.
6. Repeat these steps for every WorkOS environment.

## Role policy

The WorkOS role policy lives in
<a
  href="https://github.com/unkeyed/unkey/blob/main/pkg/auth/workos/permissions.go"
  target="_blank"
>
  `pkg/auth/workos/permissions.go`
</a>.

| Role | Unkey permissions |
| --- | --- |
| `admin` | Full product control through `unkey:v1:{workspace_id}:**#*`, including root keys |
| `developer` | Normal product access, including API key decryption, but no root keys |
| `viewer` | Read-only product access, with no API key decryption |

The `developer` and `viewer` mappings list each permission. They do not use a
recursive wildcard. A new catalog entry requires an explicit policy update
before either role receives it.

Each JWT authentication entry with `provider = "workos"` uses this role policy.
The configured issuer does not select role mapping.

We intend to add an `owner` role. This role will hold workspace-level
actions such as workspace deletion. The dashboard will reject attempts to
remove an owner from the team.

## Expansion

The JWT resolver verifies the issuer, audience, signature, and time claims. It
preserves the `roles` claim. The WorkOS provider integration then sets the
principal's permissions. It adds the resolved workspace ID to each permission:

```plaintext
Role: developer
Unkey permission: unkey:v1:{workspace_id}:projects/*/keyspaces/*/keys/*#read
```

Handlers receive API-owned resource permissions. Handlers do not depend on
WorkOS role names.

## Unknown roles

An unknown or empty role maps to no permissions. The resolver logs the role and
continues with the known roles from the same token.
