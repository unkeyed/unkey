Resource commands such as `unkey projects list` and `unkey keys get` share the flags below. The legacy `unkey api` paths accept the same flags. These output options don't apply to `unkey login`, `unkey deploy`, or `unkey healthcheck`.

<ParamField body="--root-key" type="string">
  Root key used for the request. Falls back to `UNKEY_ROOT_KEY`, then stored credentials. See [CLI authentication](/platform/cli/authentication) for the full precedence order.
</ParamField>

<ParamField body="--api-url" type="string" default="https://api.unkey.com">
  Base URL of the API. Falls back to `UNKEY_API_BASE_URL`. You don't normally need to set it.
</ParamField>

<ParamField body="--config" type="string" default="~/.unkey/config.toml">
  Path of the TOML config file. Falls back to `UNKEY_CONFIG`. An explicit `--config` takes precedence over a stored CLI session. A custom file is read as-is and is not copied into the keychain. `unkey login --root-key=-` writes the keychain, or `~/.unkey/config.toml` when the keychain is unavailable. It does not write a custom config path.
</ParamField>

<ParamField body="--output" type="enum" default="human">
  <CLIOutput />
</ParamField>

<ParamField body="--json" type="boolean">
  Print the full response as JSON. Takes precedence over a valid `--output` or `UNKEY_OUTPUT` value.
</ParamField>

<ParamField body="--debug" type="boolean">
  Print the successful response's request ID to stderr, labeled `Request ID:`. It stays separate from stdout, including when you use `--json`.
</ParamField>

<ParamField body="--error-format" type="enum" default="human">
  Select `human` or `json` for errors on stderr, including flag parsing, missing inputs, and API failures. This is independent of success output: `--json` alone does not change errors.
</ParamField>

<ParamField body="--body" type="string">
  A JSON request body to send instead of building one from the command's flags. Commands without a request body, such as `unkey workspace flags get` and `unkey workspace limits`, don't accept this flag. See [Send a raw body](#send-a-raw-body).
</ParamField>

## Output formats

The default `human` format shows name-first summary tables for lists, labeled details for individual resources, and a confirmation for actions without response data. For example, `unkey projects list` shows the name, slug, and update time in a terminal:

```plaintext
NAME      SLUG      UPDATED
Payments  payments  2 hours ago
```

Summaries use names or slugs for projects, apps, environments, domains, permissions, and roles. Lists retain IDs where you need them to identify a resource for another command. Labeled details and JSON responses retain the IDs returned by the API.

Terminal tables show relative timestamps such as `2 hours ago`. When stdout is redirected to a file or pipe, human-readable timestamps use RFC3339 in UTC, such as `2026-10-28T12:00:00Z`. JSON timestamps keep the API's original representation.

To fit the terminal width, tables shorten only display names and descriptions with an ellipsis (`…`). Identifiers, slugs, and credentials remain complete, including names used to identify resources. If the remaining columns still don't fit, the CLI prints labeled records instead of truncating identifiers. Redirected output isn't shortened. Labeled details retain exact values without width-based shortening.

An empty list prints a message instead of a table:

```plaintext
No projects found.
```

Mutations print a confirmation such as `Key created.`, `Settings updated.`, or `Variables saved.` before returned data. When the response has no data or returns assignments, the CLI also shows available request targets such as the key ID or project, app, and environment. It does not echo credentials or variable values from the request. An asynchronous action prints a message such as `Deletion requested.` instead of claiming the work has finished.

Clearing role or permission assignments prints `Roles updated.` or `Permissions updated.`, followed by `No roles assigned.` or `No permissions assigned.` An empty list operation still prints `No roles found.` or `No permissions found.`

Human environment-variable lists hide values by default. Add `--reveal` to `unkey environments variables list` to show recoverable values. Write-only values show `not retrievable`. An empty recoverable value shows `(empty)` when revealed. JSON preserves returned values regardless of `--reveal`, so treat redirected JSON as sensitive data.

Key creation and reroll show the key ID before the complete returned key. Human mode also writes a storage warning to stderr. Ordinary keys cannot be retrieved later unless created as recoverable, with the required encryption and decryption access. Root key plaintext cannot be retrieved later. JSON mode does not add a storage warning.

Tables select fields for readability. They aren't a complete representation of the response. Use `--json` or `--output=json` to get every field, including `meta`, `data`, and `pagination` when present. JSON mode preserves the full response envelope and writes only JSON to stdout:

```bash
unkey keys get --key-id=key_1234abcd --json | jq '.data.enabled'
unkey projects list --output=json | jq '.data'
```

Use JSON mode explicitly in scripts, even when redirecting output to a file or a pipe. Set `UNKEY_OUTPUT=json` to select it for every resource command in a shell session. Both `--output` and `UNKEY_OUTPUT` accept only `human` and `json`; unsupported values fail instead of falling back to human output. An explicit valid `--output` overrides `UNKEY_OUTPUT`, including an invalid environment value. Help and offline discovery remain available when `UNKEY_OUTPUT` is invalid.

When more results are available, human output includes a hint to repeat the command with `--cursor`. JSON output includes the API's pagination fields instead. Keep the same filters when requesting the next page:

```bash
unkey projects list --limit=25 --search=payments
unkey projects list --limit=25 --search=payments --cursor='<cursor>'
```

If you use `--body`, the hint tells you to set `cursor` inside the JSON body instead. Keep the other request fields and don't combine `--body` with `--cursor`:

```bash
unkey projects list --body='{"limit":25,"search":"payments","cursor":"<cursor>"}'
```

Successful human output does not show the request ID by default. Add `--debug` when you need it for troubleshooting. JSON output still includes `meta.requestId`, with or without `--debug`.

## Interactive prompts

Canonical resource commands such as `unkey projects create` ask for required inputs that are missing. Update commands also ask what to change when you supply only the target. Both stdin and stderr must be terminals.

```bash
unkey projects create
unkey projects update --project=payments
unkey deployments promote
```

The CLI keeps fields you supply as flags and asks only for missing fields. Nested objects and lists have their own prompts, so you don't need to write JSON for those inputs. If additional settings are offered, select **Continue** when finished.

Each answered or supplied field stays above the current question as one line, such as `✓ Name Acme Billing`, with nested objects and lists indented below it. Before an action, select the action, such as **Create project**, to proceed. Select **Back** to edit fields, omit an optional field, or change a list item, then select **Continue** to return to the action. Nested edits keep the other entered fields. Secrets, environment variable values, and arbitrary JSON values show as `[hidden]`. Select **Cancel** or press Ctrl+C to stop without sending the request. Destructive commands still require their separate confirmation.

Read-only commands, such as lists and searches, run after you finish selecting filters. They don't ask you to confirm a request.

The summary uses **Yes** and **No** for booleans and distinguishes **Clear (null)**, **(empty text)**, and **(no items)**. It stays human-readable on stderr even with `--json`; the JSON response on stdout is unchanged.

Prompts use your terminal theme's colors. Set `NO_COLOR` to any value, or `CLICOLOR=0`, to turn color off; labels and values are then separated by a colon. When `TERM=dumb`, prompts don't move the cursor: each question is printed on its own line, and choices are numbered so you type a number.

Complete commands run directly unless you pass `--interactive`. Review does not add a prompt to scripts or complete flag-based commands.

<ParamField body="--interactive" type="boolean">
  Ask for inputs even when all required fields are supplied. Use this for optional settings, list filters, or search fields. Requires terminals on stdin and stderr. You can't combine it with `--body` or `--no-input`.
</ParamField>

<ParamField body="--no-input" type="boolean">
  Never ask for input. Missing required flags fail instead of opening prompts. This doesn't confirm destructive commands. Use `--yes` separately when needed.
</ParamField>

Lists with no missing required fields run immediately unless you pass `--interactive`. For example, `unkey projects list --interactive` lets you set search text and a page limit:

```bash
unkey projects list --interactive
unkey keys create --api-id=api_1234abcd --interactive
```

In interactive updates, fields you don't select remain omitted and unchanged. Where the field supports it, **Clear (null)** sends `null`. Choosing **No** sends `false`, entering zero sends `0`, and submitting a list with no items sends `[]`. These values aren't the same as leaving a field out.

### Correct rejected input

If the API rejects the input with field errors, the CLI lists each rejected field with the API's message and offers **Edit answers**. Your answers stay in memory until the command exits. Edit the rejected field, check the summary, and select the action again to send the corrected request. Selecting **Cancel** returns the API error. The CLI does not resend an unchanged request.

This correction flow applies to the API's `invalid_input` 400 response with field errors. It does not reopen input for permission failures, conflicts, other 400 responses, or 422 resource-limit errors. Resource commands do not automatically retry API requests, including network and 5xx failures. A failed mutation may have completed. Check its state before running it again.

### Choose existing resources

Resource selectors offer **Browse existing resources** or **Enter ID manually** for projects, apps, environments, keys, root keys, permissions, roles, identities, rate limit namespaces and overrides, deployments, domains, and gateway policies. Selectors without a browser, such as API IDs, use text input.

Browsing asks for parent scope when needed, such as a project's app and environment. **Search** sends a filter to the API where the list endpoint supports search. An empty search clears that filter. **Next page** uses the API's pagination cursor when more results are available.

Manual ID entry doesn't require list permission. If loading choices fails, the CLI falls back to manual entry. The final request still requires the endpoint's permissions.

### Keep scripts noninteractive

Prompts are available only on canonical resource commands, not legacy `unkey api` paths. An explicit `--body`, `--no-input`, or `--interactive=false` disables them. Redirecting stdin or stderr also disables automatic prompts. Explicit `--interactive` fails when either isn't a terminal.

Prompts go to stderr, leaving stdout for the result. Redirecting only stdout or selecting `--json` doesn't disable prompts when stdin and stderr remain terminals. Use `--no-input` in scripts to make that choice explicit:

```bash
unkey projects create --name=Demo --slug=demo \
  --no-input --json --error-format=json
```

## Find command options

Use `--help` to list commands or read a command's flags, requirements, and examples. Help works without credentials or API requests.

```bash
unkey --help
unkey projects create --help
unkey gateway policies update --help
```

## Send a raw body

Normally a command builds its request from its flags, one per request field, and checks them before sending. If you already have the request as JSON, for example from a file or another tool, pass it with `--body` instead:

```bash
unkey keys create --body='{"apiId":"api_1234abcd","name":"Payment service","enabled":true}'
```

Rules for `--body`:

- It must be one JSON value that matches the endpoint's request. Most endpoints accept an object. `unkey ratelimit multi-limit` accepts an array.
- Unknown fields fail before anything is sent, so a typo in a field name doesn't get silently ignored.
- You can't combine it with the command's request flags. Required flags aren't needed either, so `unkey keys create --body='...'` doesn't also need `--api-id`.
- Authentication, API URL, configuration, and output flags still work.

## Confirm destructive commands

Delete commands and the commands that remove environment variables, key roles, or key permissions ask for confirmation before sending the destructive request. The same rule applies to canonical and legacy paths, with request flags or `--body`. Promotion, rollback, stop, and general update commands don't use this confirmation.

The prompt appears on stderr and shows the target from your request. It doesn't infer an environment:

- Environment variable removal shows the requested project, app, environment, and variable names.
- App and project deletion warn that all their environments are affected.
- Other targets show their requested IDs, slugs, names, or identifiers. Key deletion distinguishes permanent erasure from soft deletion.

Enter `y` or `yes` at `[y/N]` to proceed. An empty answer, any other answer, or end of input cancels with a nonzero exit status. Both stdin and stderr must be terminals. If either is redirected, the command refuses to proceed and tells you to use `--yes`.

In scripts, pass `--yes` to confirm explicitly. Use `--json` separately when you need a machine-readable response:

```bash
unkey keys delete --key-id=key_1234abcd --yes --json
unkey projects delete --body='{"project":"payments"}' --yes --json
```

`--yes` skips only the local prompt. It does not bypass authentication, permissions, or delete protection. `--json` and `--body` do not imply confirmation. Redirecting only stdout also does not imply confirmation; the CLI can still prompt if stdin and stderr remain terminals.

## Terminal output and scripts

Resource commands write results to stdout. Confirmation prompts, secret-storage warnings, debug request IDs, and errors go to stderr, so they don't become part of a JSON pipe. Human output remains the default when stdout is redirected; choose `--json` explicitly in scripts.

`unkey deploy` writes progress and deployment context to stderr, then final deployment details and domains to stdout. It does not support JSON output. Deployment spinners and colors require stderr to be a terminal. `TERM=dumb` disables both, and a nonempty `NO_COLOR` disables color without disabling a terminal spinner. Redirected stderr contains plain progress messages. See [Deploy output](/compute/cli/deploy).

`unkey login` writes the confirmation code, browser URL, instructions, and waiting messages to stderr. Only the final success goes to stdout. `unkey logout` also keeps diagnostics separate from its success message, including any notice that another stored workspace is now active. See [CLI authentication](/platform/cli/authentication).

## Errors and exit codes

A failed command writes its error to stderr and exits with status 1. Resource action errors start with `Error: unkey <command> failed.` and give recovery guidance. API errors include a labeled `Request ID:` when the response provides one, even without `--debug`. These diagnostics never become part of stdout or its JSON response.

| Status | Message |
| --- | --- |
| 400, 422 | The detail and invalid fields, with fix suggestions when available. Locations use matching flags or body paths when `--body` is active. |
| 401 | `Authentication failed: ...` with guidance for the active credential override or stored login. |
| 403 | `Permission denied: ...`. Check the credential, target workspace, and required access. |
| 404 | `Not found or not accessible: ...`. The response does not distinguish absence from insufficient access. |
| 409, 412 | Resolve the conflict or prerequisite. `--yes` does not bypass permissions or protection. |
| 429 | Wait before retrying and follow any retry delay reported by the API. |
| 5xx, network failure | A mutation may have completed. Check resource state before retrying to avoid duplicate changes. |

Use `--error-format=json` to get an `error` object on stderr with `message` and optional `status`, `type`, `requestId`, `hint`, and `fields`. This does not include raw HTTP response bodies. Local action errors without an HTTP status still include `message`. This option does not change success output or exit codes.

Flag input diagnostics use stable `urn:unkey:cli:<kind>` types, such as `missing_required_flag`, `invalid_flag_value`, or `conflicting_flags`. Their `fields[].location` entries identify flags such as `--name`. Invalid flag values are not echoed. Validation guidance uses the declared flag help instead of arbitrary validator messages.

Completed API calls exit 0, including empty lists, accepted asynchronous actions, and key verification responses with `valid: false`. A verification `NOT_FOUND` can mean a missing or inaccessible key. It does not prove the key is absent. Help and version requests (`--help`, `-h`, `help <command>`, `--version`, `unkey version`) exit 0 without calling the API.

## Flag syntax

`--api-id=api_123` and `--api-id api_123` are the same. A boolean flag on its own (`--enabled`) means true, and you can write `--enabled=false`. Flags can go before or after positional arguments. An unknown flag fails right away, and the message lists the flags the command accepts.
