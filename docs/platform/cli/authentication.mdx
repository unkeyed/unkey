Every CLI command that calls the API needs a root key, the same one you'd send in `Authorization: Bearer`. The usual way is to sign in once with `unkey login`. You can also pass a key with a flag or an environment variable.

## Sign in with `unkey login`

```bash
unkey login
```

The command prints a confirmation code and a URL, and opens that URL in your browser. Sign in, check that the code matches the terminal, and select the permissions the new root key should have. Allowing the login finishes it. The CLI stores the key in the system keychain and does not print the secret. When the keychain is unavailable, it writes `~/.unkey/config.toml` (mode `0600`) instead. Run it again to replace the stored key. See [unkey login](/platform/cli/login).

`unkey auth login` does the same thing.

You must be a workspace admin to approve the login. The stored key receives only the permissions you select. See [Root key permissions](/platform/root-keys/permissions).

The file fallback holds the key in plain text, so treat that file like the key. Keep it out of version control and off shared machines.

To store a key you already have, without a browser, run this and paste the key at the hidden prompt:

```bash
unkey login --root-key=-
```

That flag does not check the key with the API. A wrong key only shows up on your next `unkey api` call.

## Override the stored key

For one command, pass `--root-key`:

```bash
unkey api keys get-key --key-id=key_1234abcd --root-key=unkey_xxx
```

For a whole shell session, set `UNKEY_ROOT_KEY`:

```bash
export UNKEY_ROOT_KEY=unkey_xxx
unkey api keys get-key --key-id=key_1234abcd
```

## Which key `unkey api` uses

`unkey api` commands use the first key they find:

1. The `--root-key` flag.
2. The `UNKEY_ROOT_KEY` environment variable.
3. The system keychain, when `--config` is the default `~/.unkey/config.toml`.
4. The `root_key` value in the config file. A different `--config` or `UNKEY_CONFIG` path is read as a file and is not copied into the keychain.

If there's no key anywhere, the command stops before calling the API with `no root key provided`. If the API rejects the key, you get `Authentication failed: ...` and a hint to run `unkey login`.

## `unkey deploy` doesn't read the stored key

`unkey deploy` only takes a key from `--root-key` or `UNKEY_ROOT_KEY`. It never reads the system keychain or `~/.unkey/config.toml`, so `unkey login` doesn't help it. In CI, set `UNKEY_ROOT_KEY` as a secret. Locally, export it in the shell you deploy from. See [unkey deploy](/compute/cli/deploy).

## Point at a different API host

`--api-url` (or `UNKEY_API_BASE_URL`) sets the base URL for `unkey api` commands and for `unkey login`. `unkey deploy` has `--api-base-url`. The default is `https://api.unkey.com`. You don't normally need to change it.
