Every CLI command that calls the API needs a credential. Humans sign in once with `unkey login`. CI and other machines pass a root key with a flag or an environment variable.

## Sign in with `unkey login`

```bash
unkey login
```

The command prints a confirmation code and a URL, and opens that URL in your browser. Sign in, check that the code matches the terminal, and choose what the CLI can do. Authorizing the login finishes it. The CLI stores one session per workspace in the system keychain and does not print the tokens. When the keychain is unavailable, it writes `~/.unkey/sessions.json` (mode `0600`) instead. See [unkey login](/platform/cli/login).

`unkey auth login` does the same thing.

You can approve the login with any permission your role includes. The session receives only the permissions you select. See [Root key permissions](/platform/root-keys/permissions).

The file fallback holds the key in plain text, so treat that file like the key. Keep it out of version control and off shared machines.

To store a key you already have, without a browser, run this and paste the key at the hidden prompt:

```bash
unkey login --root-key=-
```

That flag does not check the key with the API. A wrong key only shows up on your next `unkey api` call.

## Override the stored key

For one command, pass `--root-key`:

```bash
unkey api keys get-key --key-id=key_1234abcd --root-key=unkey_xxx
```

For a whole shell session, set `UNKEY_ROOT_KEY`:

```bash
export UNKEY_ROOT_KEY=unkey_xxx
unkey api keys get-key --key-id=key_1234abcd
```

## Which key `unkey api` uses

`unkey api` uses the first credential it finds:

1. The `--root-key` flag.
2. The `UNKEY_ROOT_KEY` environment variable.
3. An explicit `--config` file. That file wins over a stored CLI session. `UNKEY_CONFIG` and the default path do not.
4. The CLI session from `unkey login`, when it belongs to the API this command is calling.
5. A root key from `unkey login --root-key`. A key still in `~/.unkey/config.toml` is used before the keychain, because that file only exists when the last save could not reach the keychain. A different `--config` or `UNKEY_CONFIG` path is read as a file and is not copied into the keychain.

`unkey deploy` has no `--config` flag. It uses `--root-key`, then `UNKEY_ROOT_KEY`, then the CLI session, then the saved root key.

If there's no credential anywhere, the command stops before calling the API with `no credentials provided`. If the API rejects the credential, you get `Authentication failed: ...` and a hint to run `unkey login`.

In CI, set `UNKEY_ROOT_KEY` as a secret. See [unkey deploy](/compute/cli/deploy).

## Point at a different API host

`--api-url` (or `UNKEY_API_BASE_URL`) sets the base URL for `unkey api` commands and for `unkey login`. `unkey deploy` has `--api-base-url`. The default is `https://api.unkey.com`.

`unkey login` stores that URL with the session. Later commands send the session to the same URL. If you pass `--api-url` or `--api-base-url` for a different host, the CLI skips the session and uses a root key instead. You don't normally need to change the URL.
