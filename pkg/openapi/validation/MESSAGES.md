# Validation messages, before and after

Every message shape this package can produce, captured by running identical
requests through both implementations: current `main` on the left, this change on
the right. Generated by a harness that posts one fixture per keyword, so
regenerate it rather than editing it by hand.

Four things changed, and they show up throughout.

**`location` points into the request, not the schema.** It used to be a pointer to
the keyword that failed, `/properties/nested/items/properties/inner/minLength`. It
is now the path a developer can find in the body they sent,
`body.nested[0].inner`. Our published `ValidationError.yaml` documented the second
form all along.

**Every problem is reported.** The old code took the first top-level failure and
discarded the rest, so a request with a bad header and three bad fields heard
about one of them.

**Nothing echoes the request.** Messages are built from the schema, so the value
that failed, its length, and its magnitude stay out. The marked cases below are
the ones where the old message handed the caller their own bytes back, which also
meant writing them into the request log.

**An unknown property suggests the one you probably meant.** The name that was
sent cannot be repeated, but the declared name it sits one edit away from can be,
so `{"neded": ...}` answers `Did you mean 'needed'?` without quoting the typo.

## additionalProperties

The old output contains bytes the caller sent.

Before

```
detail   POST request body for '/body' failed to validate schema
/additionalProperties   additional properties 'unexpected' not allowed
```

After

```
detail   POST request body for '/body' failed to validate schema
body   contains 1 property that is not defined in the schema
    fix: Remove any property that is not one of: choice, const, deps, enum, exactly, exclusiveMaximum, exclusiveMinimum, maxItems, maxLength, maxProperties, maximum, minItems, ….
```
